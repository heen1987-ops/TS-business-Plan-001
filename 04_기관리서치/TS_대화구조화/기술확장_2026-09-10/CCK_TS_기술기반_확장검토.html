국민이 조건을 설명하고, 공식 결과를 이해하고, 필요한 조치·신청을 마칠 수 있도록 CCK의 로컬 LLM·지식검색·업무 실행 기술을 조합한다. 기존 A/B/C를 포함한 5개 사업군과 이를 보완하는 2개 기능으로 확장했다.

확장 가치가 큰 지점은 여러 문서의 근거를 연결하고, 빠진 조건을 확인하고, 사람이 승인한 다음 실제 처리 상태까지 이어주는 구간이다. 텍스트 자료만으로 시험 가능한 검사결과·시정조치 검토를 먼저 구체화하고, 예약은 공식 API 확보를 병행하는 것이 현재 근거에서의 검증 순서 제안이다.

대상 독자는 CCK·TS 사업기획 검토자다. 기술 확장과 신규사업 구체화 요청으로 해석한다. G: 원본은 읽기 전용으로 참조하고, 기존 후보 선정 상태를 바꾸지 않는다. 5개는 기능·문제에 따른 사업군이며 확정 사업 수가 아니다.

증거 범위: 참조 대화·프로젝트 지침, CCK 파생 기술대장 K01과 방법론 K02·K03, 이번에 선별 열람한 공식 업무소개 O01~O09. 심층리서치 1~6 결과 본문은 이전과 같이 미열람이며 이 문서로 복원하지 않았다. 사회문제의 규모·최신 사고통계를 새로 조사한 보고서는 아니다.

1. CCK 기술을 사업 기능으로 바꾸기

아래는 자료에 기재된 자산을 활용하는 설계 가설이다. A1(기존 자산·확인 필요)에 해당하는 출발 근거이며, 검증된 기존 자산 A0로 판정하지 않았다. 지식·규칙 적응 R2, 업무 흐름 조합 R3, API·어댑터 추가 R4를 중심으로 좁히고 코어 변경은 별도 검토한다. 기술 재사용 비율·공수 절감률을 추정하지 않았다.

CCK 기술과 기능의 연결
기술·자산문서 기재사업 기능 연결적응·추가 개발증거 한계

TA-01 · Argus 계획·데이터 전달Planner → Executor → DataFlowManager 및 Core/Plugin 분리 구조가 기재지적사항별 근거·조치·증빙을 나누어 검토하고 앞 단계 결과를 다음 단계에 전달R2 업무 적응 + R3 단계 조합. 분할 처리와 결과 누락 여부 확인, 코어 수정 필요 시 별도 공수회계 도메인·클라우드 사례의 TS 로컬 전환은 미검증. 제품명·프레임워크 설명 충돌 확인 필요

TA-03 · Nexus 호출 관리LLM 호출 관리·사용량·로그 기능이 기재허용된 로컬 모델 호출, 업무별 제한과 오류 추적R1 호출 정책 + R4 로컬 엔드포인트. 외부 전송 차단, 구조화 출력·문맥 한계·부하 확인기재된 다중 클라우드 운영과 로컬 호환성은 별도. GPU 처리량·응답시간 실측 없음
업무 규칙·권한·검토 UIK02·K03에서 규칙·DB·도구·사람 검토의 책임 분리 방법을 설명필수조건 검증, 승인 화면, 공식 완료 응답·근거 이력업무별 신규 SI 범위. 현재 CCK 모듈로 되는 부분과 새로 구현할 부분을 데모로 분리설계 방법을 완제품 기능으로 간주하지 않음. NL2SQL+Evidence Trail(TA-23)은 계획 단계이므로 선행 자산으로 사용하지 않음

주관사로서 CCK의 핵심 납품은 업무 의미를 처리하는 로컬 AI, 근거 연결, 단계별 검토·실행, 품질 검증과 전체 통합이다. UI·인증·인프라·기존 시스템 연계는 협력 분담할 수 있지만, 인수 기준과 운영 책임을 CCK가 관리할 수 있어야 한다. 특정 협력사·인력이 확보됐다는 의미는 아니다.

2. 작은 범위로 납품하는 기술 구조

계층구성필수 경계
입력·증거사용자 텍스트 · 전자문서 · 공식 결과 JSON원문 위치, 문서 버전, 사용권, 기준시점 보존
CCK 처리로컬 LLM · RAG · 단계별 검토조건 해석, 근거 연결, 확인 질문, 차이 설명
업무 통제규칙 · 권한 · 상태 · 사람 확인숫자·기한·자격은 공식 규칙. 승인한 내용과 실행 요청 결속
공식 업무 연결허용된 API · 접수 · 결과 확인가용성·확정·완료는 공식 시스템 응답. 실패·미확인 구분

실시간 빈자리·자격·기한 계산은 RAG 검색 결과로 대신하지 않는다. 조회는 허용된 API와 매개변수 검증을 거치고, LLM 구조화 출력은 스키마·업무규칙으로 다시 검사한다. 근거 문서의 지시문이 도구 실행 권한을 바꾸지 못하도록 입력 자료와 시스템 정책을 분리한다.

문서 대조는 먼저 관계형 테이블의 항목 ID와 근거 위치로 시작할 수 있다. 전 기관 온톨로지나 자유 NL2SQL을 선행 구축할 필요가 있다는 주장은 하지 않는다. 검색 전 사용자·기관·문서 권한을 적용하고 캐시·벡터DB·로그·모델 호출까지 같은 접근 경계를 유지하도록 설계한다.

제안 데이터 계약의 설명용 예시. CCK 제품의 현행 스키마가 아니다.

설명 초안 → 사람 확인 → 실행 요청 → 결과 확인의 상태는 별도로 저장한다. 업무별 필요한 승인 절차를 새로 설계하고, Keeper의 Task 제어를 외부 시스템의 트랜잭션 보장으로 취급하지 않는다. 타임아웃 시 공식 상태조회로 결과를 확인하고, 확인 전에는 완료로 표시하거나 같은 쓰기 요청을 반복하지 않는다.

로컬 적합성 확인 항목: 모델·버전·양자화·라이선스, 한국어 도메인 문서의 구조화 출력과 근거 일치, 분할·재통합 시 항목 누락, 임베딩·재순위화의 로컬 실행, 허용 도구 호출, 네트워크 외부 전송 차단, 장문·동시 요청의 응답시간과 GPU 메모리. 자산의 클라우드 실적과 시험 조건이 다르므로 실제 측정 전 숫자를 제시하지 않는다.

3. 확대할 5개 사업군

X01~X05는 이번 문서에서 기술·납품 단위로 정리한 식별자다. 기존 A/B/C와 비교 주제의 연결을 유지하며 정식 후보 원장에 5건을 추가한 것이 아니다. 모든 사업군의 상태는 주관 수행 검증 전이다.

확대 범위 요약
사업군이전 조사 연결핵심 작동먼저 확인
X01 조건을 알아듣는 예약·신청 실행기존 A 구체화실행 연계형공식 조회 가능성부터 확인
X02 검사·리콜 결과에서 후속 행동까지기존 B + 리콜 비교 주제 통합결과 이해형결과 표본으로 먼저 기술 검증
X03 위험·결함 보고를 정확하게 전달기존 C + 자동차 결함신고 적용 검토사실 전달형제도 하나의 보호·서식부터 확인
X04 안전 지적사항의 조치·증빙 연결기계식주차장 비교 주제 확장증거 대조형문서 쌍으로 먼저 기술 검증
X05 복잡한 신청의 준비·보완 지원기관 자격·튜닝 업무로 적용 확대요건 대조형계약 비중복·보완 사례부터 확인

X01 · 조건을 알아듣는 예약·신청 실행

기존 A 구체화 · 실행 연계형 · 주관 수행 검증 전

검사 이용자가 가능한 날짜·장소를 반복해서 뒤지지 않고 자신의 일정에 맞는 선택지를 찾고 예약하도록 돕는다.

설명용 예시: ‘검사 기한 안에서 평일 오후에 갈 수 있고, 집에서 너무 멀지 않은 곳을 찾아줘. 없으면 토요일도 볼게.’

핵심 처리: 로컬 LLM이 필수조건과 선호조건을 구조화 → 사용자 확인 → 허용 목록의 조회 API → 규칙으로 부적합 슬롯 제거 → LLM이 대안의 차이를 설명 → 동의·재조회 후 예약 요청 → 공식 확정 결과 표시.

기술·납품·책임·검증 상세

조사 근거와 한계

T05~T08에 사용자의 마감 확인·화면 왕복 경험과 자연어 대안 탐색 요구가 있다. O01에서 자동차검사 업무와 검사소 찾기·사이버검사소 연결을 확인했다. 현재 UI 불편 발생률과 실시간 API는 확인하지 않았다.

TS 접점·권한

자동차검사 예약 접점. 시험·교육 예약으로의 확대는 별도 시스템·권한·소관을 확인한다. 공식 소개의 업무 존재를 확인한 수준이며 개별 위탁·법령 시행일 대조는 미완료.

입력

차량·검사종류·공식 검사기간, 이용자가 확인한 날짜/시간/이동 범위, 공식 검사소·슬롯 데이터와 조회시각.

CCK 재사용

TA-01·02·03의 단계 실행과 TA-20의 절차 검색을 재사용 검토. R2 검사규칙, R3 조건 변경 흐름, R4 슬롯·예약 어댑터가 중심. 자유 SQL 생성은 사용하지 않는다.

추가 개발

조건 편집 UI, 공식 조회 커넥터, 후보 정렬, 조회시각·마감/조회불가 표시, 승인한 슬롯과 요청 ID 결속, 중복방지 키·타임아웃 후 상태조회·재개 흐름.

직접·협력 책임

CCK: 조건 해석·대안 설명·전체 연계와 품질. 협력사: 예약 화면·인증·기존 예약 서버 어댑터 등 확보된 범위. TS/운영사: 공식 가용정보·권한·예약 처리 책임.

필수 외부 조건

공식 다중 검사소/날짜 조회, 차량 적합성·기간 확인, 인증·예약/취소 인터페이스. 공개 웹 화면의 존재만으로 API 제공·접근권한을 가정할 수 없다.

최소 납품

조건 확인·대안 UI, 조회/실행 커넥터, 예외 처리, 규칙·프롬프트, 검수 시나리오, 운영·장애 대응 문서. API 확보 수준별 납품 범위를 계약에 분리.

비AI 비교

달력·필터·마감 표시 개선을 기준안으로 삼는다. 복합 조건 해석과 대안 수정에서 추가 가치가 없으면 단순 UX 개선으로 분류한다.

검증할 성과

유효 후보를 찾는 시간·왕복·재입력, 필수조건 보존, 실제 예약 완료율, 마감 슬롯 제시·허위 완료·중복 요청 오류. 평가안이며 목표값·효과 실측은 미확정.

실패 처리

조회 실패는 빈자리 없음과 구별. 확정 요청의 타임아웃은 결과 미확인으로 두고 상태를 확인한 뒤 재시도. LLM이 기한·자격·빈자리·완료를 생성하지 않는다.

중복·축소 기준

설명용 예시: ‘지금 가진 자격·검사 결과로 어느 단계부터 진행해야 하고, 제출할 설명에서 빠진 내용은 무엇인지 알려줘.’

핵심 처리: 일상어 설명을 요건 항목에 대응 → 모르는 사실 확인 → 규칙으로 선행 단계·필수 자료 대조 → LLM이 부족한 내용과 이유 설명 → 신청자가 수정·동의 → 서식 출력 또는 공식 접수 연결.

기술·납품·책임·검증 상세

조사 근거와 한계

O06에서 사업용 운송자격 취득의 검사·시험·교육 등 단계가, O09에서 튜닝 신청·첨부·승인·작업·검사 흐름이 확인된다. 실제 반려·보완 원인과 일반 안내 이후의 잔여 문제는 미검증이다.

TS 접점·권한

한 자격 신청의 준비·보완을 첫 도메인으로 검토. 튜닝은 텍스트 신청 요건·누락 대조에만 패턴 확장하며 도면 판독·안전 설계심사는 포함하지 않는다.

입력

사용자가 확인한 이력, 권한 있는 공식 자격·검사상태, 승인된 절차표, 텍스트 신청서·자료 목록·보완 통지. 민감 이력의 불필요한 수집은 피한다.

CCK 재사용

TA-20의 기준·서식 검색과 TA-01의 요건별 검토를 사용 검토. R2 절차·서식·지식 적응, R3 확인·보완 흐름, R4 이력·접수 연결.

추가 개발

요건-증빙 스키마, 기준 버전, 항목별 누락·불일치 표시, 보완 전후 대조, 규칙 평가기, 사용자 확인 UI. 자격 판정·튜닝 안전 승인은 기존 권한자에게 남김.

직접·협력 책임

CCK: 요건 연결·설명·보완 검토·워크플로 통합. TS 업무전문가: 적용 기준과 예외 검수. 협력사: 신청 화면·이력/접수 어댑터.

필수 외부 조건

정확한 요건표·유효한 서식·예외 처리자, 기존 민원·직무특화 과업과의 비중복, 전자 원본. 튜닝 문서가 도면·사진 판독 중심이면 해당 적용은 축소한다.

최소 납품

한 신청 유형의 준비·보완 도우미, 규칙/서식 패키지, 원문-요건 대조 UI, 출력·연계, 변경관리와 오류 시나리오·운영 문서.

비AI 비교

절차 안내표·조건형 폼·필수값 검증과 비교. 비정형 설명의 요건 연결·보완 사유 이해에서 이점이 없으면 별도 AX 후보로 유지하지 않는다.

검증할 성과

첫 신청의 자료 완비, 불필요한 보완·반복 방문, 잘못된 자격 안내, 필수자료 누락·임의 사실 생성, 이의·정정 처리. 공식 승인율을 AI 정확도와 동일시하지 않는다.

실패 처리

예외·기준 충돌·이력 미조회는 확정 안내를 멈추고 담당 확인. 신청서 출력과 접수, 접수와 승인을 구분한다.

중복·축소 기준

민원 SFR-006~007 및 직무특화 SFR-003과의 중복 위험이 크다. 상담을 넘어 실제 신청의 준비·보완 문제와 미포함 산출물이 확인된 유형만 남긴다. X01의 슬롯 탐색과 같은 기능은 공동 사용.

확산 경로

자격·교육·신청 도메인마다 요건·서식·이력 API를 바꾸어 적용. 일반적인 범정부 민원 플랫폼을 새로 구축하는 안으로 확대하지 않는다.
