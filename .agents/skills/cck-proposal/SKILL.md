# 제안서 작성

[공통 계약](../_shared/contract.md)과 [근거 규칙](../_shared/evidence-rules.md)을 읽는다. 기관 공통 자료보다 먼저 현재 공고와 정정 차수, 제출 양식, 평가표, 실제 지원/입찰 주체를 식별한다.

## 입력

공고/RFP/평가기준/양식, 사업 목적·예산·기간·제출 조건, 제안 주체의 검증 가능한 실적·인력·제품·협력 근거, 제안할 범위·가정. 없는 정보는 UNKNOWN으로 남기고 무근거 실적·보유 기능·확정 인력·협약·선정을 생성하지 않는다.

## 절차

1. INFORMATION_SYSTEM 조달 제안인지 R_AND_D 신청/계획인지 구분한다. R&D는 해당 공고의 신청 자격·연구 목표·평가항목·협약/연구비 조건을 확인하고 일반 정보화 RFP 목차를 그대로 강제하지 않는다.
2. `requirement_id | 원문/위치 | 필수/평가/참고 | 조건 | 평가기준/배점 | 답변 절/페이지 | 근거 | 충족상태/미결` 매트릭스를 만든다. 배점·양식·분량·접수 방식·마감은 해당 공고에서 읽은 값을 사용한다. 정정과 본문/상단 기간이 다르면 충돌을 표시한다.
3. 문제·성과목표→접근방법→실행계획→산출물→검증→비용/일정의 연결을 설계한다. 공통 근거를 재사용하되 기관·사업·공고별 요구를 분리한다.
4. 각 주장을 EXISTING_EVIDENCE(확인 근거), PROPOSED(계획/제안), ASSUMPTION(가정), UNKNOWN(미확인)으로 표시한다. 경쟁력 문구나 목표 성능을 현재 실적처럼 쓰지 않는다. 인력 배치는 실제 참여 가능 근거가 없으면 계획으로 적는다.
5. 요구/평가항목별 누락, 무근거 수치, 비용·일정·범위 불일치, 금지/제한 조건, 양식 차이를 검토한다. 익명성·서명·확약·제출파일 조건은 공고에서 확인하고 없으면 필요한 확인으로 남긴다.
6. 제안 초안, 대응 매트릭스, 증거 목록, 가정/위험/미확인표를 함께 제공한다. 공개·제출 전 확인 사항을 구체적으로 제시한다. 실제 제출은 이 스킬의 결과로 자동 발생하지 않는다.

## 수행 인계

수주/선정 이후에는 제안 주장→협상/선정 결과→계약/협약 조항→승인 계획을 대조한 인계표를 만든다. 계약 편입 여부와 승인 증거가 불명확한 약속은 미결로 유지한다. 제안서 파일이나 선정 안내만으로 사업관리의 승인 기준선을 만들지 않는다.

## 산출물

제안서/연구개발계획서 초안, 공고별 요구·평가 대응표, 증거 원장, 수치·일정 가정표, 제출 조건 검토표, 수행 인계표. 제출 준비 완료나 선정 가능성은 구조 검사 통과만으로 판정하지 않는다.
