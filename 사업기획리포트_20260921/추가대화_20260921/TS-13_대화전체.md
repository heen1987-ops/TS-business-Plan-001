## 3. 먼저 구분할 것: ‘부적격’과 ‘미확인’은 같은 상태가 아님

공개된 부산본부 자료에는 부적격 사례의 상세 유형·산식·발생 원인까지 제시되어 있지 않습니다. 따라서 연령, 검사 미수검, 교육 미이수, 자격상태 등의 항목을 임의로 합쳐 **‘부적격자 정의’를 새로 만들지 않습니다.** 실제 업종별 법령·업무기준·공식 관리유형부터 확인해야 합니다. :chatgpt-content-reference{index="5"}

이번 서비스에서는 다음 상태를 구분하는 방안을 제안합니다. 이는 **법정 분류가 아니라 검토·처리를 위한 설계안**입니다.

| 구분 | 의미 | 필요한 대응 |
|---|---|---|
| **요건 미충족이 확인됨** | 해당 업종·대상·시점에 적용되는 요건의 미충족이 공식 근거로 확인됨 | 권한 있는 담당자가 법정·내부 절차에 따른 조치 수행 |
| **확인자료가 부족함** | 필요한 조회·증빙을 확보하지 못해 결론을 내릴 수 없음 | 추가 확인 또는 승인된 대체 확인절차 |
| **정보가 서로 불일치함** | 공식 조회정보·제출자료·등록정보의 대상이나 시점 등이 맞지 않음 | 원천기관 확인, 사실관계 대조, 정정 필요성 검토 |
| **조치 후 결과확인이 남음** | 종사자나 회사가 조치했다고 보고했지만 공식 결과·반영 여부가 확인되지 않음 | 적정한 결과인지 확인하고 관리정보 반영 |
| **해당 요건의 충족을 확인함** | 정해진 범위에서 요건 충족이 확인됨 | 확인근거·시점·적용범위를 기록 |

**‘조회되지 않음’을 ‘부적격’으로 바꾸거나, ‘경고가 없음’을 ‘모든 운행요건 충족’으로 바꾸지 않는 것**이 핵심입니다.

또한 행정적 요건 충족 여부와 개인의 운전능력·사고 가능성은 구분합니다. 이번 컨셉은 법정 요건의 확인과 후속처리를 지원하는 것이지, 사람의 위험성을 종합평가하는 서비스가 아닙니다.

## 4. 해결하려는 문제는 세 가지

### ① 자격·검사·소속 등의 변화가 실제 업무에서 어떻게 반영됐는지 확인하기 어려울 수 있음

**문제 가설**

> 운수종사자와 관련된 상태가 변경됐을 때, 원천에서 사실이 발생한 시점, 관리시스템에 반영된 시점, 회사가 확인한 시점이 구분되지 않으면 어느 정보가 현재 판단에 유효한지 다시 확인해야 할 수 있다.

확인할 것은 다음과 같습니다.

**무엇이 언제 바뀌었는가 → 어느 시스템에 반영됐는가 → 실제 관리대상 회사와 연결됐는가 → 누가 확인했는가**

예를 들어 소속변경이나 정보정정이 있었는데 과거 관계가 남은 경우와, 실제로 필요한 조치가 이행되지 않은 경우는 다른 문제입니다. 이는 가능한 원인 예시이며, 실제 발생 여부는 검증해야 합니다.

**첫 질문:** “변경된 사실을 처음 알 수 있었던 시점과 실제 업무에 반영한 시점 사이에 어떤 확인이 필요했습니까?”

### ② 알림을 받아도 무엇을 어떻게 해야 하는지 명확하지 않을 수 있음

**문제 가설**

> 회사 담당자나 종사자가 알림을 받았지만 적용사유·확인기관·필요자료·완료조건을 이해하지 못하면, 같은 내용을 다시 문의하거나 필요한 조치가 늦어질 수 있다.

여기서 필요한 것은 알림 횟수를 늘리는 것이 아니라 **알림을 실행 가능한 안내로 바꾸는 것**입니다.

| 알림 이후의 질문 | 제공해야 할 정보 |
|---|---|
| 왜 나에게 해당하는가? | 확인된 대상·업종·사유·기준시점 |
| 무엇을 해야 하는가? | 공식적으로 필요한 확인 또는 조치 |
| 어디에 문의해야 하는가? | 해당 사실·결과를 확인할 권한 있는 창구 |
| 무엇을 제출해야 하는가? | 실제 필요한 자료와 제출방법 |
| 언제 끝난 것으로 보는가? | 조치결과·정보반영을 확인하는 기준 |

단, 기존 알림이 이미 이 내용을 충분히 제공하고 있고 사용자가 정상적으로 처리한다면, 별도의 대화형 서비스는 필요하지 않을 수 있습니다.

### ③ 조치완료 보고와 실제 해소 여부가 연결되지 않을 수 있음

**문제 가설**

> 종사자가 검사·자료보완 등을 마쳤다고 보고했거나 회사가 조치결과를 제출했더라도, 공식 결과와 관리정보의 반영 여부를 다시 대조해야 한다면 미해결 상태가 오래 남거나 잘못 종결될 수 있다.

여기서도 **예약, 방문, 검사 실시, 해당 기준 충족, 관리정보 반영은 서로 다른 상태**로 검토해야 합니다.

반대로 적격 상태가 공식적으로 확인됐는데 이전 경고가 계속 남는다면, 이는 불필요한 문의뿐 아니라 종사자에게 불이익을 줄 수 있는 정보처리 문제로 다뤄야 합니다.

### TS-13 통합 문제정의

> **운수종사자 관리에서 공식적인 요건 확인·알림 이후, 회사와 종사자의 실제 조치 및 그 결과의 확인·반영까지 연결하는 데 누락·지연·정보불일치가 남아 있는지 검증한다. 이를 자료·시점 문제, 안내 이해 문제, 실제 미이행, 기관 간 확인대기로 구분하고, 원인에 맞는 지원기능을 구성한다.**

**고의 미준수나 실제 자원 부족이 원인이라면 문서 AI만으로 해결할 수 없습니다.** 기존 관리·감독·검사 제공체계의 조정이 필요한 문제와 분리합니다.

## 5. 서비스는 어떻게 구성하는가

큰 흐름은 다음과 같습니다.

**공식 상태 확인 → 해당 사유와 필요한 행동 설명 → 회사·종사자의 조치 → 공식 결과 대조 → 관리정보 반영 확인 → 잔여사항 관리**

이를 세 가지 구성요소로 묶습니다.

| 구성요소 | 지원할 내용 | 확보하려는 결과 |
|---|---|---|
| **① 운행요건·변경사항 확인지원** | 공식 조회결과의 대상·시점·적용범위와 관련 문서를 연결하고 불일치·미확인 항목 제시 | 어떤 사실을 근거로 무엇을 확인해야 하는지 파악 |
| **② 종사자·회사별 조치 안내** | 같은 사건이라도 종사자가 할 일, 회사가 할 일, 원천기관이 확인할 일을 구분 | 알림 이후 필요한 행동과 담당기관 이해 |
| **③ 조치결과·정정 반영 확인** | 제출한 자료, 공식 처리결과, 관리정보를 대조하고 남은 사항 표시 | 실제 해소 여부와 미완료 원인을 확인 |

서비스의 관리단위는 ‘위험한 사람 한 명’이 아니라 **특정 대상의 특정 요건 확인 건**으로 두는 것이 적절합니다.

> **종사자 참조 → 적용 업종·업무 → 확인할 요건 → 공식 상태·시점 → 필요한 조치 → 결과 근거 → 확인·반영 상태**

이렇게 해야 한 번의 미확인 상태가 사람 전체에 대한 고정적인 평가로 남지 않습니다. 같은 사람이라도 사유와 적용기간이 다르면 다른 확인 건으로 관리합니다.

### 대표 적용 예시: “검사를 받았는데 미확인 알림이 계속 오는 경우”

다음은 실제 TS 사건이 아닌 **설명용 시나리오**입니다.

종사자가 필요한 검사를 이미 받았다고 설명하지만, 회사가 확인하는 시스템에는 해당 검사이력의 추가 확인이 필요하다고 표시되는 상황을 가정합니다.

| 단계 | 서비스 지원 | 사람이 확인·수행할 내용 |
|---|---|---|
| **대상·사유 확인** | 어떤 검사·기간·대상의 정보인지 정리 | 이번 알림이 실제로 해당 종사자에게 적용되는지 확인 |
| **자료 대조** | 제출자료의 검사종류·일자·대상과 공식 조회결과의 차이 표시 | 단순 예약·방문기록인지, 필요한 검사결과인지 확인 |
| **원인 구분** | 자료부족·유형 불일치·반영 지연 등 확인할 질문 제시 | 원천기관이 사실관계와 유효한 결과를 확인 |
| **후속조치 연결** | 필요한 수검·자료보완·정보정정 절차를 설명 | 당사자·회사·기관이 각자의 조치 수행 |
| **종결 검토** | 공식 결과와 관리정보 반영 여부를 연결 | 권한 있는 담당자가 해당 확인 건의 해소 여부 판단 |

결과는 미리 정하지 않습니다.

실제로 필요한 검사를 받지 않았다면 적절한 수검·확인절차가 필요합니다. 다른 종류의 검사자료를 제출했다면 그 차이를 설명해야 합니다. 유효한 결과가 있는데 반영만 늦었다면 원천 확인과 정정·반영이 핵심입니다.

**AI가 서류 한 장을 읽었다는 이유로 운행 가능 상태를 직접 만들어내거나, 조회실패만으로 운행을 금지하는 방식은 제외합니다.** 안전상 즉시 확인이 필요한 사안은 기존 공식 대응절차로 넘기고, AI의 추가 해석을 기다리게 하지 않습니다.

종사자가 정보오류를 설명하고 정정을 요청할 경로도 포함합니다. 생성형 AI의 설명은 공식 판단과 구분하고, 담당자가 원근거를 확인해 수정·거부할 수 있어야 합니다. ‘사람 승인 버튼’만 추가하고 실질적인 검토가 없는 구조는 피합니다.

## 9. 어떤 사업으로 만들 것인가

### 권고하는 초기 사업형태

**부산본부가 제기한 문제 중 현재도 남아 있는 한 가지 관리사유를 선정하고, ‘확인·통보 이후 실제 해소까지’의 연결을 검증하는 방식**을 권고합니다.

시내버스·택시·화물 전체를 동시에 묶지 않습니다. 먼저 업종 하나에서 원천자료·판단기준·실제 처리주체를 확보해야 합니다.

| 대안 | 제공범위·기대효과 | 비용·기간의 성격 | 선행조건·필요자료 |

**권고는 A로 해결되는 범위를 먼저 제거하고, 설명·예외검토가 실제로 남는 부분에 B를 적용하는 것입니다.** 데이터 갱신 오류를 해결하지 않은 채 챗봇만 붙이면 잘못된 상태를 더 유창하게 설명하게 될 수 있습니다.

### CCK의 공급·수익 구조

사업이 성립하면 **업무·사유별 요구정의, 기존 시스템 연계, 증빙·회신 검토, 사용자별 조치 안내, 현장검증·운영지원**을 공급범위로 구성합니다.

| **종사자 권익** | 잘못된 경고·정보오류를 설명·정정하는 부담과 불이익이 줄었는가 | 적격자의 불필요한 배제 증가를 안전성과로 포장 |
| **전체 업무부담** | 재문의·자료 대조·정정 부담 감소가 신규 검수·운영비보다 큰가 | 입력량이나 처리보고서 수를 성과로 사용 |

**부적격률만 낮아졌다는 결과로 성공을 판단하지 않습니다.** 관리대상·분모·분류방식이 달라지거나 기록에서 제외된 경우에도 숫자는 낮아질 수 있습니다. 반대로 확인체계가 좋아져 초기 발견 건수가 늘어날 수도 있습니다.

따라서 같은 업종·관리사유·기간·집계단위를 기준으로 **실제 요건 미충족의 해소, 잘못된 분류의 정정, 후속조치 누락 감소**를 함께 확인하는 평가안이 필요합니다. 사고감소는 별도의 장기 효과평가로 다루고, 알림 개선만으로 입증했다고 표현하지 않습니다.

### 첫 현업 확인질문

> **“2025년에 공개한 협의체·합동점검·알림·교육 이후에도 남은 사례를 보면, 문제는 처음에 발견하지 못한 것입니까, 통보 후 조치하지 않은 것입니까, 조치결과가 관리정보에 반영되지 않은 것입니까?”**

처음 확보할 자료는 **업종별 공식 관리유형, 가림처리된 실제 사례, 상태변경·통보·회신·조치·정정 기록, 기존 시스템의 후속처리 기능**입니다. 동일 사건을 처음부터 끝까지 따라가야 데이터 문제와 실제 미이행을 구분할 수 있습니다.

현재 공개자료로 확인한 것은 **부산본부의 당시 문제 제기와 개선계획, 기존 자격관리·알림의 목적, 관련 부서**입니다. 운수종사자관리시스템의 로그인 이후 기능, 2026년 잔여사례·원인별 규모, 기존 개선의 효과와 추가 구매수요는 확인하지 못했으므로 신규사업성은 아직 확정하지 않습니다.

### TS-13 사업컨셉 핵심 문장

> **본 사업은 운수종사자의 업종별 운행요건을 확인한 결과가 회사와 종사자의 적절한 조치 및 공식 결과반영으로 이어지도록 지원하는 것을 목적으로 한다. 기존 자격관리·알림체계를 활용하여 확인된 사유, 적용시점, 필요한 행동, 원천정보와 조치결과를 연결하고, 실제 요건 미충족·자료부족·정보불일치·반영대기를 구분한다. 개인정보와 종사자의 정정·설명 기회를 보호하면서, 기존 시스템과 절차로 해결되지 않는 사유 해석·예외검토·후속처리 범위만 추가 구축한다.**

**TS-13의 차별점은 ‘부적격자를 더 많이 찾아내는 AI’가 아니라, ‘확인된 문제를 정확한 조치와 해소로 연결하고 잘못된 정보로 인한 불이익도 줄이는 AI’입니다.** 다음은 **TS-14 ‘철도와 연계교통의 실제 환승 접근성’**의 상위 사업컨셉입니다.
