## 2. 현행 기반과 고도화 목표

항공 자격 안내·경력 증빙·신청 시스템을 이용하는 업무에 항공 자격 지식·경력 서술 대조·신청 연계 항목을 추가한다. 현행 내부 화면·소요시간·API를 직접 시험한 것은 아니다. 아래 흐름과 오류 처리는 **제안 설계**이며 현업 워크숍에서 실제 절차와 대조한다.

대표 상황: 응시자가 경력 설명을 제출했지만 신청하려는 자격의 요구 자료와 연결되지 않는 상황

| 현행 기반 활용 | 고도화할 처리 | 유지할 공식 책임 |
| --- | --- | --- |
| 항공 자격 안내·경력 증빙·신청 시스템 | 항공 자격 신청자의 경력 서술과 증빙을 요구자료에 연결하는 응시 준비 지원 | 기존 업무의 자격·검사·예약·지급·공개·안전 판단 권한 |
| 자격별 구조화 문진표와 제출서류 체크리스트 | 경력 서술과 자격별 준비자료 비교, 개인별 설명·보완 질문 | 원천 데이터·적용 기준의 승인과 검토자 확인 |


국민에게 기대하는 가치는 정확한 다음 행동과 보완 필요를 더 빨리 이해하거나, 담당자의 검토 누락을 줄이는 것이다. 다음 지표를 측정해 확인한다: 잘못된 준비자료 안내·보완 요구 재발·신청 준비시간. 업무시간 절감을 감축 인원으로 환산하지 않는다. 사고 감소·무사고를 이 기능만으로 입증했다고 주장하지 않는다.

## 4. 처리 흐름과 화면

목표 자격 확인 → 경력 최소 문진 → 증빙 연결 → 보완 확인 → 이용자 확인 → 공식 신청 인계. 경력 산입·응시 판정은 권한 있는 절차가 수행한다.

| 순서 | 사용자·시스템 동작 | 처리 책임 |
| --- | --- | --- |
| 1 | 항공 자격 종류와 기준일을 고정하고 타 자격 자료를 구분한다. | LLM은 제안·설명, 규칙·권한·원천 상태는 응용 계층에서 검증 |
| 2 | 서술의 기간·단위·발급 주체를 증빙과 대응시킨다. | LLM은 제안·설명, 규칙·권한·원천 상태는 응용 계층에서 검증 |
| 3 | 없는 자료와 내용 불일치를 구분해 보완을 안내한다. | LLM은 제안·설명, 규칙·권한·원천 상태는 응용 계층에서 검증 |
| 4 | 준비 상태와 공식 접수를 구분하고 이용자 확인 내용을 고정한다. | 사용자/현업 확인 후 공식 시스템의 권한 유지 |


화면 TS-P07-S01은 **입력·조건 → 근거를 포함한 결과 → 사용자/담당자 확인 → 다음 처리** 순서로 구성한다. 원문 위치와 적용본은 결과 옆에서 확인하고, 확인 전 초안과 확정된 원천 상태를 구분한다. 모바일은 입력·결과·확인을 세로로 배치하며 조건을 잃지 않는다.

| 화면 상태 | 필수 동작 |
| --- | --- |
| 대기·조회 중 | 입력을 보존하고 진행 단계 표시; 확정 버튼 중복 실행 방지 |
| 자료 없음·일부만 확인 | 없는 항목과 미확인 사유, 가능한 다음 행동 표시 |
| 권한 거부 | 자료 내용을 노출하지 않고 권한 요청 또는 기존 창구 안내 |
| 오류·시간 초과 | 현재 처리 결과를 확정하지 않음; 원 상태 재조회 후 재시도 |
| 정상 결과·확인 대기 | 근거·적용본·한계를 읽고 사용자가 선택 또는 담당자가 수정 |
| 이관·확정·반려 | 공식 응답이나 담당자 결정 이력으로 상태 구분 |


화면 상세 디자인과 API 실주소는 별도 구현 단계에서 확정한다. 키보드 입력·오류 초점·상태 읽기와 모바일 조건 유지가 제품 인수 시험 대상이다.

## 5. 데이터·출력 계약

아래 필드명은 **논리 설계 예시**다. 실제 원 시스템 필드·API가 존재한다는 뜻이 아니다. 필드별 필수 여부·보존기간·마스킹·추출 가능성을 원천 담당자와 매핑표로 확정한다.

| 입력 논리 항목 | 연결·검증 규칙 |
| --- | --- |
| qualification_type / route | 선정한 항공 자격 1종과 준비 경로 |
| experience_items | 신청자가 진술한 경력 종류·기간·단위 |
| evidence_ref / issuer | 증빙 위치·발급 주체 |
| rule_id / effective_at | 적용 요건과 기준일 |
| verified_status / unknown_items | 공식 확인 상태와 미확인 항목 |
| consent / handoff_ref | 본인 확인 및 공식 신청 인계 |


출력은 다음 항목을 묶고 각 항목에 원문 참조·버전·확인 상태를 붙인다.

- 경력 진술·증빙 대응표
- 확인된 수치와 미확인 수치
- 준비자료 보완 질문
- 응시 가능 여부의 공식 확인 경로
- 이용자가 확인한 인계 요약

공통 메타데이터: case_id, source_refs, source_version, retrieved_at, rule_version, model_config_version, review_status, reviewer_action. 여기의 review_status는 제안 기능의 상태이며 법정·업무 처분 상태를 대신하지 않는다.

본인확인·상태 읽기·신청 인계는 기존 자격 시스템과 협의한다. 경력 적격 심사 엔진을 LLM으로 대체하지 않는다. P02의 진행단계 UI·오류처리만 공유한다.

자료가 없으면 승인된 파일 반입·공개 지식만으로 가능한 1단계까지 수행한다. 개인 데이터 조회·쓰기 연계가 필요한 후속 단계는 실제 인터페이스와 권한이 확인돼야 개발 범위를 확정한다.

## 8. 데이터 주권·안전·운영

LLM의 경력 합산이나 해석이 응시 자격 판정처럼 보일 위험. 공식 확인과 준비 지원을 결과 필드에서 구분한다.

- 자료 원본·검색 인덱스·모델 호출·로그·백업·라이선스 경로를 기존 서버 환경에서 점검한다. 로컬 배치라는 이유만으로 외부 전송이 없거나 보안이 충족됐다고 단정하지 않는다.
- 문서 안의 명령·외부 링크는 근거 데이터로 취급하고 실행 지시로 사용하지 않는다. 인용 권한은 검색과 원문 열람 모두에서 검증한다.
- 기준·문서 변경과 접근 철회 시 결과를 재확인 대상으로 전환하고 인덱스 갱신·삭제 전파 방법을 검증한다. 보존기간과 삭제 권한은 TS 정책 확인 후 설정한다.
- 기존 업무 화면을 복귀 경로로 보존하고 AI 기능만 비활성화할 수 있게 한다. 쓰기 도입 시 요청 식별자·상태 재조회·승인·중복 방지·복구 담당을 계약에 명시한다.

법정업무 확인 범위: 공식 안내의 항공안전법 제34조·제109조 업무 확인. 응시 요건의 현행 시행본·심사권한 미확정. 실제 현행 조문·위탁 관계·개인정보 처리 근거의 최종 적용 검토는 착수 전 확인 항목이다.

P02와 자격 지원 구조 공유; 항공 경력 인정·증명서·심사 규칙 별도 기존 계약의 동일 납품분과 공통 모듈은 신규 작업으로 중복 청구하지 않는다.

신규 서버·GPU·저장/백업/망 구매·증설·임차·클라우드 비용은 **0원**이다. 기존 환경의 설정·연계·부하 시험은 수행 공수에 포함 가능하다. 모델 사용권·제품 라이선스가 기존 계약에 포함되는지는 확인 전이며 무상으로 단정하지 않는다. 추가 사용료가 필요하면 비용·대안을 확정하고 상한 안에서 범위를 조정한다.
