## 2. 현행 기반과 고도화 목표

철도 안전관리체계 검사·요건·제출/보완 기록을 이용하는 업무에 요건팩·증빙 연결·기관 권한·검사 사례 평가 항목을 추가한다. 현행 내부 화면·소요시간·API를 직접 시험한 것은 아니다. 아래 흐름과 오류 처리는 **제안 설계**이며 현업 워크숍에서 실제 절차와 대조한다.

대표 상황: 운영기관이 절차서를 개정했지만 실제 적용 기록이 어떤 검사 요건을 충족하는지 분명하지 않은 상황

| 현행 기반 활용 | 고도화할 처리 | 유지할 공식 책임 |
| --- | --- | --- |
| 철도 안전관리체계 검사·요건·제출/보완 기록 | 철도 안전관리체계의 요건별 제출·보완·현장 확인 근거를 연결하는 검사관 검토 화면 | 기존 업무의 자격·검사·예약·지급·공개·안전 판단 권한 |
| 전문가 체크리스트·문서 버전관리·기존 철도 검사시스템 | 요건-제출자료 의미 연결과 보완 검토 | 원천 데이터·적용 기준의 승인과 검토자 확인 |


국민에게 기대하는 가치는 정확한 다음 행동과 보완 필요를 더 빨리 이해하거나, 담당자의 검토 누락을 줄이는 것이다. 다음 지표를 측정해 확인한다: 필수 증빙 누락 미발견·근거 연결 오류·보완 왕복 횟수. 업무시간 절감을 감축 인원으로 환산하지 않는다. 사고 감소·무사고를 이 기능만으로 입증했다고 주장하지 않는다.

## 4. 처리 흐름과 화면

요건 고정 → 제출자료 연결 → 보완 이력 대조 → 서류 검토 → 현장 결과 연결 → 검사관 결정. 문서상 충족 후보와 법정 검사결과는 분리한다.

| 순서 | 사용자·시스템 동작 | 처리 책임 |
| --- | --- | --- |
| 1 | 검사건의 적용 요건을 불변 참조로 저장한다. | LLM은 제안·설명, 규칙·권한·원천 상태는 응용 계층에서 검증 |
| 2 | 절차서에 규정되어 있다는 사실과 실제 이행 증빙을 구분한다. | LLM은 제안·설명, 규칙·권한·원천 상태는 응용 계층에서 검증 |
| 3 | 이전 지적별로 변경된 문서·증빙을 찾는다. | LLM은 제안·설명, 규칙·권한·원천 상태는 응용 계층에서 검증 |
| 4 | 현장 확인이 필요한 요건은 서류 검토와 별도 상태로 관리한다. | 사용자/현업 확인 후 공식 시스템의 권한 유지 |


화면 TS-P04-S01은 **입력·조건 → 근거를 포함한 결과 → 사용자/담당자 확인 → 다음 처리** 순서로 구성한다. 원문 위치와 적용본은 결과 옆에서 확인하고, 확인 전 초안과 확정된 원천 상태를 구분한다. 모바일은 입력·결과·확인을 세로로 배치하며 조건을 잃지 않는다.

| 화면 상태 | 필수 동작 |
| --- | --- |
| 대기·조회 중 | 입력을 보존하고 진행 단계 표시; 확정 버튼 중복 실행 방지 |
| 자료 없음·일부만 확인 | 없는 항목과 미확인 사유, 가능한 다음 행동 표시 |
| 권한 거부 | 자료 내용을 노출하지 않고 권한 요청 또는 기존 창구 안내 |
| 오류·시간 초과 | 현재 처리 결과를 확정하지 않음; 원 상태 재조회 후 재시도 |
| 정상 결과·확인 대기 | 근거·적용본·한계를 읽고 사용자가 선택 또는 담당자가 수정 |
| 이관·확정·반려 | 공식 응답이나 담당자 결정 이력으로 상태 구분 |


화면 상세 디자인과 API 실주소는 별도 구현 단계에서 확정한다. 키보드 입력·오류 초점·상태 읽기와 모바일 조건 유지가 제품 인수 시험 대상이다.

## 5. 데이터·출력 계약

아래 필드명은 **논리 설계 예시**다. 실제 원 시스템 필드·API가 존재한다는 뜻이 아니다. 필드별 필수 여부·보존기간·마스킹·추출 가능성을 원천 담당자와 매핑표로 확정한다.

| 입력 논리 항목 | 연결·검증 규칙 |
| --- | --- |
| operator_id / inspection_id | 운영기관과 검사건 식별자 |
| requirement_id / version | 적용 요건·기준 버전 |
| procedure_ref / revision | 절차서 위치·개정번호 |
| evidence_ref / valid_period | 운영 증빙 위치·유효 범위 |
| previous_finding / correction | 이전 지적과 현재 보완 설명 |
| field_check_status / reviewer | 현장 확인 여부와 검사관 결정 |


출력은 다음 항목을 묶고 각 항목에 원문 참조·버전·확인 상태를 붙인다.

- 요건별 문서·증빙 연결표
- 이전 지적 대비 보완 변화
- 서류 미확인과 현장 확인 필요의 구분
- 보완 질의 초안
- 검사관 확정 의견과 이력

공통 메타데이터: case_id, source_refs, source_version, retrieved_at, rule_version, model_config_version, review_status, reviewer_action. 여기의 review_status는 제안 기능의 상태이며 법정·업무 처분 상태를 대신하지 않는다.

기관별 문서·검사 결과 읽기 연계 1개를 우선한다. 법정 검사결과 등록과 현장 확인은 기존 권한을 유지한다. P05와 검색·증빙 위치 기능을 공유하되 요건팩을 분리한다.

자료가 없으면 승인된 파일 반입·공개 지식만으로 가능한 1단계까지 수행한다. 개인 데이터 조회·쓰기 연계가 필요한 후속 단계는 실제 인터페이스와 권한이 확인돼야 개발 범위를 확정한다.

## 8. 데이터 주권·안전·운영

절차서 존재와 운영 이행을 혼동할 위험. 요건별 증거 종류를 별도로 강제한다.

- 자료 원본·검색 인덱스·모델 호출·로그·백업·라이선스 경로를 기존 서버 환경에서 점검한다. 로컬 배치라는 이유만으로 외부 전송이 없거나 보안이 충족됐다고 단정하지 않는다.
- 문서 안의 명령·외부 링크는 근거 데이터로 취급하고 실행 지시로 사용하지 않는다. 인용 권한은 검색과 원문 열람 모두에서 검증한다.
- 기준·문서 변경과 접근 철회 시 결과를 재확인 대상으로 전환하고 인덱스 갱신·삭제 전파 방법을 검증한다. 보존기간과 삭제 권한은 TS 정책 확인 후 설정한다.
- 기존 업무 화면을 복귀 경로로 보존하고 AI 기능만 비활성화할 수 있게 한다. 쓰기 도입 시 요청 식별자·상태 재조회·승인·중복 방지·복구 담당을 계약에 명시한다.

법정업무 확인 범위: 공식 안내의 철도안전법 제7조·시행령 제63조 위탁 근거 확인. 적용 시행본·세부 권한 원문 대조 필요. 실제 현행 조문·위탁 관계·개인정보 처리 근거의 최종 적용 검토는 착수 전 확인 항목이다.
