## 2. 현행 기반과 고도화 목표

결함 신고·수리내역·조사/소비자 지원 절차을 이용하는 업무에 사건 식별·시간순 대조·본인 확인·원문 추적 항목을 추가한다. 현행 내부 화면·소요시간·API를 직접 시험한 것은 아니다. 아래 흐름과 오류 처리는 **제안 설계**이며 현업 워크숍에서 실제 절차와 대조한다.

대표 상황: 소유자가 수차례 같은 증상을 겪었으나 수리내역에 표현이 달라 사건의 순서가 혼동되는 상황

| 현행 기반 활용 | 고도화할 처리 | 유지할 공식 책임 |
| --- | --- | --- |
| 결함 신고·수리내역·조사/소비자 지원 절차 | 자동차 증상·수리·재발 진술을 원문과 연결해 소비자와 조사 담당자가 확인하는 사건 정리 지원 | 기존 업무의 자격·검사·예약·지급·공개·안전 판단 권한 |
| 시간순 입력 양식과 제출서류 체크리스트 | 수리·증상 연표와 사실/불확실 구분, 신청자 확인·사건 요약 | 원천 데이터·적용 기준의 승인과 검토자 확인 |


국민에게 기대하는 가치는 정확한 다음 행동과 보완 필요를 더 빨리 이해하거나, 담당자의 검토 누락을 줄이는 것이다. 다음 지표를 측정해 확인한다: 사건 순서 오류·근거 없는 사실 추가·보완 문의 왕복. 업무시간 절감을 감축 인원으로 환산하지 않는다. 사고 감소·무사고를 이 기능만으로 입증했다고 주장하지 않는다.

공개 NOA 소개와 내부 TA-01·02·03·20 기록은 재사용 후보의 근거다. 실제 납품 버전의 구현·성능·사용권 증명이 아니며 부족한 업무 기능은 CCK의 설정·개발·시험 과업으로 산정한다. TA-23 NL2SQL·Evidence Trail은 계획 기능이므로 현재 보유 기능으로 계상하지 않는다. 상세 기술 근거는 공통 보고서에 연결했다.

## 4. 처리 흐름과 화면

소유자 입력 → 전자기록 연결 → 사건 정리 → 상충 질문 → 본인 확인 → 담당자 인계. 결함·보상·리콜 판단은 별도 공식 절차다.

| 순서 | 사용자·시스템 동작 | 처리 책임 |
| --- | --- | --- |
| 1 | 차량과 사건 식별키를 고정하고 비슷한 증상을 가진 타 차량 기록을 분리한다. | LLM은 제안·설명, 규칙·권한·원천 상태는 응용 계층에서 검증 |
| 2 | 발생·수리·재발의 시점과 원문 근거를 연결한다. | LLM은 제안·설명, 규칙·권한·원천 상태는 응용 계층에서 검증 |
| 3 | 진술과 증빙의 날짜·주행거리가 다르면 차이를 설명해 소유자에게 묻는다. | LLM은 제안·설명, 규칙·권한·원천 상태는 응용 계층에서 검증 |
| 4 | 확인된 사실 묶음만 인계하고 법적·기술적 결론은 생성하지 않는다. | 사용자/현업 확인 후 공식 시스템의 권한 유지 |


화면 TS-P12-S01은 **입력·조건 → 근거를 포함한 결과 → 사용자/담당자 확인 → 다음 처리** 순서로 구성한다. 원문 위치와 적용본은 결과 옆에서 확인하고, 확인 전 초안과 확정된 원천 상태를 구분한다. 모바일은 입력·결과·확인을 세로로 배치하며 조건을 잃지 않는다.

| 화면 상태 | 필수 동작 |
| --- | --- |
| 대기·조회 중 | 입력을 보존하고 진행 단계 표시; 확정 버튼 중복 실행 방지 |
| 자료 없음·일부만 확인 | 없는 항목과 미확인 사유, 가능한 다음 행동 표시 |
| 권한 거부 | 자료 내용을 노출하지 않고 권한 요청 또는 기존 창구 안내 |
| 오류·시간 초과 | 현재 처리 결과를 확정하지 않음; 원 상태 재조회 후 재시도 |
| 정상 결과·확인 대기 | 근거·적용본·한계를 읽고 사용자가 선택 또는 담당자가 수정 |
| 이관·확정·반려 | 공식 응답이나 담당자 결정 이력으로 상태 구분 |


화면 상세 디자인과 API 실주소는 별도 구현 단계에서 확정한다. 키보드 입력·오류 초점·상태 읽기와 모바일 조건 유지가 제품 인수 시험 대상이다.

## 5. 데이터·출력 계약

아래 필드명은 **논리 설계 예시**다. 실제 원 시스템 필드·API가 존재한다는 뜻이 아니다. 필드별 필수 여부·보존기간·마스킹·추출 가능성을 원천 담당자와 매핑표로 확정한다.

| 입력 논리 항목 | 연결·검증 규칙 |
| --- | --- |
| case_id / vehicle_ref | 사건·차량 최소 식별키; 타 차량 병합 금지 |
| symptom_text / observed_at | 소유자의 증상 진술과 발생 시점 |
| repair_ref / repair_date | 전자 수리내역의 원문과 작업일 |
| mileage / unit | 기록된 주행거리와 단위; 추정 보충 금지 |
| recurrence / uncertainty | 재발 진술·날짜 불명·상충 내용 |
| owner_confirmation / review_ref | 소유자 확인 및 담당자 인계 이력 |


출력은 다음 항목을 묶고 각 항목에 원문 참조·버전·확인 상태를 붙인다.

- 발생→수리→재발 사건표
- 각 사실의 진술/증빙 출처
- 날짜·차량·주행거리 상충
- 본인 확인 질문
- 확인된 사실과 미확인 주장을 구분한 인계 자료

공통 메타데이터: case_id, source_refs, source_version, retrieved_at, rule_version, model_config_version, review_status, reviewer_action. 여기의 review_status는 제안 기능의 상태이며 법정·업무 처분 상태를 대신하지 않는다.

사용자가 제공한 텍스트·전자 수리내역을 우선한다. 차량·수리 이력 조회는 소유자 동의와 허용 범위가 확인된 경우에만 추가하며 조사·중재 인계 권한은 기존 절차를 따른다.

자료가 없으면 승인된 파일 반입·공개 지식만으로 가능한 1단계까지 수행한다. 개인 데이터 조회·쓰기 연계가 필요한 후속 단계는 실제 인터페이스와 권한이 확인돼야 개발 범위를 확정한다.

## 8. 데이터 주권·안전·운영

서술을 매끄럽게 만드는 과정에서 사실과 추정을 합칠 위험. 진술·문서·확인 상태를 각각 저장한다.

- 자료 원본·검색 인덱스·모델 호출·로그·백업·라이선스 경로를 기존 서버 환경에서 점검한다. 로컬 배치라는 이유만으로 외부 전송이 없거나 보안이 충족됐다고 단정하지 않는다.
- 문서 안의 명령·외부 링크는 근거 데이터로 취급하고 실행 지시로 사용하지 않는다. 인용 권한은 검색과 원문 열람 모두에서 검증한다.
- 기준·문서 변경과 접근 철회 시 결과를 재확인 대상으로 전환하고 인덱스 갱신·삭제 전파 방법을 검증한다. 보존기간과 삭제 권한은 TS 정책 확인 후 설정한다.
- 기존 업무 화면을 복귀 경로로 보존하고 AI 기능만 비활성화할 수 있게 한다. 쓰기 도입 시 요청 식별자·상태 재조회·승인·중복 방지·복구 담당을 계약에 명시한다.

법정업무 확인 범위: KATRI 공식 제작결함·자기인증·교환환불 업무 확인. 결함 인정·보상·리콜 결정 권한을 AI에 이전하지 않음. 실제 현행 조문·위탁 관계·개인정보 처리 근거의 최종 적용 검토는 착수 전 확인 항목이다.
