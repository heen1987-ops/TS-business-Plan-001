## 2. 현행 기반과 고도화 목표

안전기준·시험계획·안내문·서식 관리을 이용하는 업무에 안전기준군 1개·문서 영향·담당자 검토·발행 상태 항목을 추가한다. 현행 내부 화면·소요시간·API를 직접 시험한 것은 아니다. 아래 흐름과 오류 처리는 **제안 설계**이며 현업 워크숍에서 실제 절차와 대조한다.

대표 상황: 시험보고서 양식은 개정됐지만 공개 안내가 이전 기준을 설명하는 상황

| 현행 기반 활용 | 고도화할 처리 | 유지할 공식 책임 |
| --- | --- | --- |
| 안전기준·시험계획·안내문·서식 관리 | 미래차 안전기준 개정이 시험계획·서식·안내문에 미치는 영향을 검토하고 반영 이력을 추적하는 지원 | 기존 업무의 자격·검사·예약·지급·공개·안전 판단 권한 |
| 문서 버전관리·변경 알림·담당자 체크리스트 | 개정 기준의 영향 문서 후보와 반영 확인 목록 | 원천 데이터·적용 기준의 승인과 검토자 확인 |


국민에게 기대하는 가치는 정확한 다음 행동과 보완 필요를 더 빨리 이해하거나, 담당자의 검토 누락을 줄이는 것이다. 다음 지표를 측정해 확인한다: 필수 반영 대상 누락·잘못된 영향 제시·오래된 안내 잔존. 업무시간 절감을 감축 인원으로 환산하지 않는다. 사고 감소·무사고를 이 기능만으로 입증했다고 주장하지 않는다.

## 4. 처리 흐름과 화면

기준 개정 등록 → 적용 범위 확인 → 영향 후보 검색 → 담당자 채택/기각 → 문서 수정 → 승인 → 발행 확인. 초안 수정과 실제 배포를 분리한다.

| 순서 | 사용자·시스템 동작 | 처리 책임 |
| --- | --- | --- |
| 1 | 국내외 기준과 시행일·경과 적용을 별도 필드로 둔다. | LLM은 제안·설명, 규칙·권한·원천 상태는 응용 계층에서 검증 |
| 2 | 변경 조항과 영향을 받는 문서 부분을 함께 제시한다. | LLM은 제안·설명, 규칙·권한·원천 상태는 응용 계층에서 검증 |
| 3 | 담당자가 영향 후보를 채택·기각하고 사유를 기록한다. | LLM은 제안·설명, 규칙·권한·원천 상태는 응용 계층에서 검증 |
| 4 | 문서의 승인본과 실제 발행 버전을 비교한다. | 사용자/현업 확인 후 공식 시스템의 권한 유지 |


화면 TS-P14-S01은 **입력·조건 → 근거를 포함한 결과 → 사용자/담당자 확인 → 다음 처리** 순서로 구성한다. 원문 위치와 적용본은 결과 옆에서 확인하고, 확인 전 초안과 확정된 원천 상태를 구분한다. 모바일은 입력·결과·확인을 세로로 배치하며 조건을 잃지 않는다.

| 화면 상태 | 필수 동작 |
| --- | --- |
| 대기·조회 중 | 입력을 보존하고 진행 단계 표시; 확정 버튼 중복 실행 방지 |
| 자료 없음·일부만 확인 | 없는 항목과 미확인 사유, 가능한 다음 행동 표시 |
| 권한 거부 | 자료 내용을 노출하지 않고 권한 요청 또는 기존 창구 안내 |
| 오류·시간 초과 | 현재 처리 결과를 확정하지 않음; 원 상태 재조회 후 재시도 |
| 정상 결과·확인 대기 | 근거·적용본·한계를 읽고 사용자가 선택 또는 담당자가 수정 |
| 이관·확정·반려 | 공식 응답이나 담당자 결정 이력으로 상태 구분 |


화면 상세 디자인과 API 실주소는 별도 구현 단계에서 확정한다. 키보드 입력·오류 초점·상태 읽기와 모바일 조건 유지가 제품 인수 시험 대상이다.

## 5. 데이터·출력 계약

아래 필드명은 **논리 설계 예시**다. 실제 원 시스템 필드·API가 존재한다는 뜻이 아니다. 필드별 필수 여부·보존기간·마스킹·추출 가능성을 원천 담당자와 매핑표로 확정한다.

| 입력 논리 항목 | 연결·검증 규칙 |
| --- | --- |
| standard_id / jurisdiction | 기준 식별자와 국내·해외 관할 |
| old_version / new_version | 비교할 원문 버전과 개정 조항 |
| effective_at / transition | 시행일·경과 규정의 확인 상태 |
| document_id / owner | 시험계획·서식·안내문 및 책임부서 |
| impact_ref / reason | 영향 후보의 원문 위치·사유 |
| approved_revision / published_at | 승인된 변경본과 실제 발행 확인 |


출력은 다음 항목을 묶고 각 항목에 원문 참조·버전·확인 상태를 붙인다.

- 개정 전후 조항 차이
- 영향 문서·담당자 목록
- 직접 영향 / 검토 필요 / 관련 없음
- 반영 의견과 원문 근거
- 승인·발행·미반영 상태

공통 메타데이터: case_id, source_refs, source_version, retrieved_at, rule_version, model_config_version, review_status, reviewer_action. 여기의 review_status는 제안 기능의 상태이며 법정·업무 처분 상태를 대신하지 않는다.

문서 저장소·발행 상태 읽기와 변경 검토 이력 연결을 우선한다. 실제 문서 배포는 기존 승인 절차를 유지한다. P13과 버전 차이·영향 근거 엔진을 공유한다.

자료가 없으면 승인된 파일 반입·공개 지식만으로 가능한 1단계까지 수행한다. 개인 데이터 조회·쓰기 연계가 필요한 후속 단계는 실제 인터페이스와 권한이 확인돼야 개발 범위를 확정한다.

## 8. 데이터 주권·안전·운영

관련 문서의 존재만으로 변경 필요를 확정할 위험. 변경 사유와 전문가 채택·기각을 추적한다.

- 자료 원본·검색 인덱스·모델 호출·로그·백업·라이선스 경로를 기존 서버 환경에서 점검한다. 로컬 배치라는 이유만으로 외부 전송이 없거나 보안이 충족됐다고 단정하지 않는다.
- 문서 안의 명령·외부 링크는 근거 데이터로 취급하고 실행 지시로 사용하지 않는다. 인용 권한은 검색과 원문 열람 모두에서 검증한다.
- 기준·문서 변경과 접근 철회 시 결과를 재확인 대상으로 전환하고 인덱스 갱신·삭제 전파 방법을 검증한다. 보존기간과 삭제 권한은 TS 정책 확인 후 설정한다.
- 기존 업무 화면을 복귀 경로로 보존하고 AI 기능만 비활성화할 수 있게 한다. 쓰기 도입 시 요청 식별자·상태 재조회·승인·중복 방지·복구 담당을 계약에 명시한다.

법정업무 확인 범위: KATRI 공식 미래차 연구·안전도평가 업무 확인. 독립 R&D와 시험설비 개발은 기획 범위 제외. 실제 현행 조문·위탁 관계·개인정보 처리 근거의 최종 적용 검토는 착수 전 확인 항목이다.
