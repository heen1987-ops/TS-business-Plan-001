# CCK AI 적용 공통 설계·추진계획·비용 산정

22개 고도화 보고서의 구현 경계와 비용 계산을 통합한 v1.0 설계안이다. 2026-09-15. [22개 보고서](00_%EA%B3%A0%EB%8F%84%ED%99%94%EB%B3%B4%EA%B3%A0%EC%84%9C_%ED%86%B5%ED%95%A9%EB%B3%B4%EA%B8%B0.html)

## 1. 결론과 가정

기존 TS 시스템에 CCK AI를 추가하는 **공통 기반 + 업무별 증분** 방식으로 추진한다. 22개는 업무별 설명 단위이며 22개의 독립 플랫폼·독립 계약이 아니다. P01/P17, P21/P22를 각각 묶으면 20개 실행 묶음이지만 이 역시 발주 건수 확정이 아니다.

기구축 시스템·기존 AI에 CCK AI를 추가 적용하는 AX+SI. NOA·로컬 LLM·기존 서버 사용. 신규 인프라 비용 0원. 비전·OCR·STT/TTS·신규 센서·물리 제어 제외. 독립 R&D 제외.

작업 유형은 공공 AX+SI 기획·설계 고도화, 규모 L, 위험도 High(원 서비스 적용 시), 방법론은 Stage-Gate·요구사항 추적·기존 기능 영향분석이다. 공식 업무와 공급사 기능 설명 → 제안 설계 → 검수 기준 → 견적 조건의 근거를 분리한다. 이번 납품은 문서이며 제품 개발·운영 배포는 수행하지 않는다.

가정: 기존 NOA 사용권과 실행환경을 활용할 수 있고, 각 보고서의 최소 적용 단위에 필요한 텍스트·공식 결과를 확보할 수 있다. 확인되지 않으면 공개 지식·승인 파일 기반 단계로 축소하거나 해당 연계를 보류한다. 기구축 사업이라는 이유로 AI 적용을 제외하지 않는다.

## 3. 구현 경계·데이터 주권

<div class="flow"><span>기존 문서·공식 결과</span><span>권한 있는 조회·적재</span><span>NOA·로컬 LLM</span><span>근거·초안·검토</span><span>확인 후 공식 처리</span></div>

LLM은 의미 추출·대조·설명·초안에 사용한다. 식별키 검증·권한·상태전이·예약 중복 방지·금액·단위·승인·쓰기 여부는 응용 계층과 기존 공식 시스템의 결정 규칙이 담당한다. LLM이 만든 도구 호출이라도 허용 목록·입력 계약·사용자 확인을 거쳐야 한다.

| 영역 | 필수 확인·설계 |
| --- | --- |
| 자료 | 텍스트 추출 가능성·필드·원문 위치·기준 버전·보존/삭제 권한. 스캔·이미지는 수동 확인 |
| 검색 | 기관/업무/역할에 따른 검색·원문 접근권한. 문서 접근 철회와 색인 갱신 시험 |
| 추론 | 모델·프롬프트·지식·도구 버전 기록. 근거 없는 사실과 공식 완료 상태 생성 금지 |
| 외부 경로 | 모델·임베딩·라이선스·로그·모니터링·백업까지 호출 경로 점검. 외부 전송 미관측이 영구 보장을 뜻하지 않음 |
| 쓰기 | 실제 API·승인·인증·요청키·상태 조회·충돌·타임아웃 계약 확인 후 도입. 초기는 읽기/초안·기존 화면 인계 우선 |
| 중단·복귀 | AI 기능 단위 비활성화, 직전 지식·설정 복원, 원 시스템 정상 사용. 실제 쓰기는 정정·취소 업무 절차로 복구 |
| 역할 | TS는 정책·자료·최종 업무 판단, CCK는 주관 구축·검증 지원, 기존 운영사는 연계·운영 호환 제공 |


허용 API가 없으면 승인 파일·공식 화면 인계로 가능한 기능까지 구현한다. 실제 시스템의 무단 화면 수집·우회 접속을 연계 대안으로 가정하지 않는다.

공통 구성의 하한은 기존 기능을 설정·연결할 수 있는 경우, 상한은 제한된 보완 구현·예외 검증이 필요한 경우를 상정했다. 실제 NOA 기능이 이미 충분하면 기존 이행 확인·설정·회귀 시험량만 남긴다. 제시 상한을 초과할 수 있는 사유는 API 신설, 법정 규칙 다수, 대규모 문서 정비, 보호 원본 사용 협의, 기존 서버 용량 부족이다. 이 경우 범위를 줄이거나 다시 산정하며 신규 인프라를 넣어 해결하지 않는다.

## 6. 예산 상한과 견적 산식

사용자 검토안은 1차 7억 원, 2차 추가 5억 원, 합계 12억 원(VAT 포함 해석)이다. 이는 프로그램 상한이며 현재 전체 22개 범위를 해당 금액에 납품할 수 있다고 확인한 것은 아니다.

- 단계 사업비 = 선택된 공통 비용 1회 + 선택 업무별 증분 인건비 + 확인된 추가 사용료·필요 경비 + 계약 방식에 따른 제경비·이윤·세금.
- 업무 증분 인건비 = Σ(역할별 인일 × 확인된 역할별 일단가). 역할별 실제 배분·단가는 견적 시 확정한다.
- 단가에 이미 포함된 관리·제경비·이윤은 별도 중복 가산하지 않는다. 법정 세금 적용은 계약 방식과 확인 단가 기준에 맞춘다.
- 1차에 구축한 공통 기능을 2차에 재구축비로 넣지 않는다. 2차의 신규 업무 지식·커넥터·평가·필요한 공통 변경·운영비만 반영한다.
- 신규 GPU·서버·저장·백업·망의 구매·증설·임차·클라우드 자원비는 0원이다. 기존 장비에서 실행될 수 있는 범위로 물량·모델·동시성을 조정한다.
- 라이선스 추가비·운영 지원비는 미확인이다. 0원이라고 가정하지 않고 기존 계약 포함 여부와 증분 견적으로 판단한다.

금액 단가를 임의 채우지 않았으므로 공수의 원화 환산표는 확정하지 않았다. 인일 범위는 견적 비교의 입력이며 기능점수 기반 공공 SW 대가 산정을 대체하지 않는다. 발주 방식에서 요구하는 산정 기준·현행 공식 단가를 정한 뒤 검증 가능한 원가표로 전환해야 한다.

실행 기간안: 자료·책임·최소 연계가 준비된 대표 묶음에 대해 1–2주 기준·데이터 확정, 3–4주 지식·읽기/화면 시범, 5–8주 연계·예외 검증, 9–12주 현업 시범·인수를 계획한다. 이는 22개 전체 납기나 실제 인력 확약이 아니다. 선택 업무 수·투입 가능 인력·승인 대기에 따라 재산정한다.

## 8. 요구사항 추적과 평가 설계

기능 88개(HF01–HF04 × 22), 업무별 공통 비기능 44개(HN01–HN02 × 22), 합계 132개 요구사항을 구성했다. 시험은 요구사항별 132개와 정상 흐름 22개로 **154개 설계 사례**다. 모두 미실행이다. 공통 비기능 44개는 업무별 적용 확인 행이며 별도 보안 기능 44개를 개발하는 물량이 아니다.

[요구사항·시험 추적 원장](03_%EC%9A%94%EA%B5%AC%EC%82%AC%ED%95%AD_%EC%8B%9C%ED%97%98%EC%B6%94%EC%A0%81.json)에서 요구→화면→보고서→시험→미실행 상태를 확인한다. 기존 v0.2 88개 요구는 기능 계보로 연결했고 동일 계약 충족으로 자동 인정하지 않는다.

평가 절차:

1. 업무별 정답·필수 누락·금지 결정·오류 심각도를 TS 현업이 정의한다. 원문·규칙·역할·모델·프롬프트 버전을 고정한다.
2. 같은 사례로 현행 처리, 화면/규칙 개선, AI 추가 결과를 비교한다. 자동 채점만 쓰지 않고 수정 전 초안과 현업 확정본을 함께 본다.
3. 첫 반복은 정상·정보 부족·상충·버전 변경·권한·외부 요청 오류를 포괄하는 최소 설계 사례로 오류 종류를 찾는다. 반복 생성은 독립 사례 수로 세지 않는다.
4. 실제 사례의 표본 수는 처리량·사례 분포·허용 오류·목표 개선 폭·가용 검수시간으로 사전 결정한다. 숫자 하나를 모든 업무의 합격 표본으로 강제하지 않는다.
5. 결과를 본 뒤 성공 기준을 낮추거나 유리한 사례만 골라 성과를 제시하지 않는다. 실패·애매함·평가자 불일치를 보존한다.
6. 중대 오류, 권한 누출, 허위 접수/종결 등은 배포 보류 후 원인·회귀 사례로 남긴다. 0건 관측을 위험 0으로 일반화하지 않는다.
7. 근거 정확성·누락·시간·사용성·운영비를 함께 보고한다. 처리시간 감소만으로 사고 감소·감축 인원을 주장하지 않는다.

성능 수치가 확정되지 않은 상태다. Gate A에서 기존 서버·모델·동시 요청·문서 길이별 기준선을 측정하고, 검수 시험 전에 목표값·측정법·허용 오차·책임자를 확정해야 성능 요구를 완료로 판정할 수 있다.
