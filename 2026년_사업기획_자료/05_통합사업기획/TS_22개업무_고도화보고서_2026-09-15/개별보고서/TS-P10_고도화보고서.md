## 2. 현행 기반과 고도화 목표

자동차검사 검색·달력·예약·결과 안내을 이용하는 업무에 가용상태 UI·조건 해석·예약 연계·중복방지 평가 항목을 추가한다. 현행 내부 화면·소요시간·API를 직접 시험한 것은 아니다. 아래 흐름과 오류 처리는 **제안 설계**이며 현업 워크숍에서 실제 절차와 대조한다.

대표 상황: 검사소를 찾았으나 날짜별 마감을 뒤늦게 확인해 조건을 다시 입력하는 상황

| 현행 기반 활용 | 고도화할 처리 | 유지할 공식 책임 |
| --- | --- | --- |
| 자동차검사 검색·달력·예약·결과 안내 | 검사소와 날짜를 오가며 마감을 확인하는 불편을 줄이는 예약 가능 상태 중심 탐색 화면 | 기존 업무의 자격·검사·예약·지급·공개·안전 판단 권한 |
| 예약 상태를 미리 보여주는 달력·검색 UI와 공식 API 개선 | 날짜·이동 범위의 자연어 조건 이해, 대안 설명, 확인 질문·예약 인계 | 원천 데이터·적용 기준의 승인과 검토자 확인 |


국민에게 기대하는 가치는 정확한 다음 행동과 보완 필요를 더 빨리 이해하거나, 담당자의 검토 누락을 줄이는 것이다. 다음 지표를 측정해 확인한다: 빈자리 탐색시간·화면 왕복·상태 불일치·중복 예약. 업무시간 절감을 감축 인원으로 환산하지 않는다. 사고 감소·무사고를 이 기능만으로 입증했다고 주장하지 않는다.

## 4. 처리 흐름과 화면

조건 입력 → 가용상태 조회 → 같은 화면 비교 → 선택 확인 → 공식 예약 요청 → 확정/마감/결과 미확인. 결과 미확인은 상태 재조회 후 재시도 여부를 결정한다.

| 순서 | 사용자·시스템 동작 | 처리 책임 |
| --- | --- | --- |
| 1 | 자연어 날짜·지역을 필수/선호 조건으로 바꾸고 이용자에게 보여준다. | LLM은 제안·설명, 규칙·권한·원천 상태는 응용 계층에서 검증 |
| 2 | 검사소 목록과 달력에 공식 가능·마감·휴무·미확인 상태를 표시한다. | LLM은 제안·설명, 규칙·권한·원천 상태는 응용 계층에서 검증 |
| 3 | 동일 날짜 다른 검사소와 같은 검사소 다른 날짜를 분리해 제시한다. | LLM은 제안·설명, 규칙·권한·원천 상태는 응용 계층에서 검증 |
| 4 | 최종 요청 전 유효 상태를 확인하고 요청 결과가 모호하면 원 시스템을 재조회한다. | 사용자/현업 확인 후 공식 시스템의 권한 유지 |


화면 TS-P10-S01은 **입력·조건 → 근거를 포함한 결과 → 사용자/담당자 확인 → 다음 처리** 순서로 구성한다. 원문 위치와 적용본은 결과 옆에서 확인하고, 확인 전 초안과 확정된 원천 상태를 구분한다. 모바일은 입력·결과·확인을 세로로 배치하며 조건을 잃지 않는다.

| 화면 상태 | 필수 동작 |
| --- | --- |
| 대기·조회 중 | 입력을 보존하고 진행 단계 표시; 확정 버튼 중복 실행 방지 |
| 자료 없음·일부만 확인 | 없는 항목과 미확인 사유, 가능한 다음 행동 표시 |
| 권한 거부 | 자료 내용을 노출하지 않고 권한 요청 또는 기존 창구 안내 |
| 오류·시간 초과 | 현재 처리 결과를 확정하지 않음; 원 상태 재조회 후 재시도 |
| 정상 결과·확인 대기 | 근거·적용본·한계를 읽고 사용자가 선택 또는 담당자가 수정 |
| 이관·확정·반려 | 공식 응답이나 담당자 결정 이력으로 상태 구분 |


화면 상세 디자인과 API 실주소는 별도 구현 단계에서 확정한다. 키보드 입력·오류 초점·상태 읽기와 모바일 조건 유지가 제품 인수 시험 대상이다.

## 5. 데이터·출력 계약

아래 필드명은 **논리 설계 예시**다. 실제 원 시스템 필드·API가 존재한다는 뜻이 아니다. 필드별 필수 여부·보존기간·마스킹·추출 가능성을 원천 담당자와 매핑표로 확정한다.

| 입력 논리 항목 | 연결·검증 규칙 |
| --- | --- |
| vehicle_class / inspection_type | 공식 검사 가능 조건 |
| date_range / time_preference | 희망 범위와 필수/선호 구분 |
| location / travel_limit | 지역·이동 한도; 사용자가 변경을 승인 |
| station_id / slot_id | 공식 검사소·예약 가능 시간 식별자 |
| availability / observed_at | 가능·마감·휴무·미확인 및 조회 시각 |
| confirmation / receipt_id | 최종 선택 확인·공식 예약번호 |


출력은 다음 항목을 묶고 각 항목에 원문 참조·버전·확인 상태를 붙인다.

- 조건을 유지한 검사소·가능 시간 목록
- 클릭 전 달력 상태
- 동일 날짜 다른 검사소 / 동일 검사소 다른 날짜 대안
- 조건을 벗어나는 대안의 변경 내용
- 예약 결과·변경/취소 경로

공통 메타데이터: case_id, source_refs, source_version, retrieved_at, rule_version, model_config_version, review_status, reviewer_action. 여기의 review_status는 제안 기능의 상태이며 법정·업무 처분 상태를 대신하지 않는다.

가용상태 조회 1개와 예약 인계/요청 1개가 핵심이다. 현재 API·화면의 실제 지원 범위는 미확인이다. API가 없으면 공식 조회 화면 개선 범위부터 확정하며 화면 수집을 공식 연계로 가정하지 않는다.

자료가 없으면 승인된 파일 반입·공개 지식만으로 가능한 1단계까지 수행한다. 개인 데이터 조회·쓰기 연계가 필요한 후속 단계는 실제 인터페이스와 권한이 확인돼야 개발 범위를 확정한다.

| TS-P10-HN01<br>접근권한·로컬 처리 | 원문·인덱스·로그·호출의 권한과 외부 경로를 점검한다. | 승인된 권한 거부 사례에서 원문·검색·직접 요청을 모두 거부하고, 기존 서버 실행 시험 중 승인되지 않은 외부 모델·데이터 전송이 관측되면 배포를 보류한다.<br>시험: TS-P10-HT05 |
| TS-P10-HN02<br>근거·실패 상태·복귀 | 원문 위치·버전·조회 시점을 표시하고 자료 실패와 실제 결과를 분리한다. | 삭제·접근 철회·변경된 자료가 탐지되면 해당 결과를 최신·확정으로 표시하지 않으며 오류 시 입력을 보존하고 기존 처리 경로를 제공한다.<br>시험: TS-P10-HT06 |


기능 HF01–HF04는 기존 기획의 4단계 기능을 구체화한 것이다. HN01–HN02는 각 업무에도 적용하는 공통 비기능 요구다. 기존 계약의 동일 요구를 이미 충족했다면 기존 납품 검증으로 인정하고 같은 개발비를 다시 계상하지 않는다. 새 테스트 사례·업무별 설정·연계 차이는 증분 작업으로 남긴다.

## 7. 합성 사례로 본 기대 결과

실제 고객·차량·신고 자료가 아닌 **설계 설명용 합성 사례**다. NOA 또는 모델에 실행한 결과가 아니다.

| 합성 상황 | 기대 처리 예시 | 금지되는 처리 |

## 8. 데이터 주권·안전·운영

LLM보다 UI·연계 품질이 효용을 좌우한다. 화면 개선만 한 비교안과 같은 조건에서 탐색시간·왕복을 비교해 AI 추가 가치를 확인한다.

- 자료 원본·검색 인덱스·모델 호출·로그·백업·라이선스 경로를 기존 서버 환경에서 점검한다. 로컬 배치라는 이유만으로 외부 전송이 없거나 보안이 충족됐다고 단정하지 않는다.
- 문서 안의 명령·외부 링크는 근거 데이터로 취급하고 실행 지시로 사용하지 않는다. 인용 권한은 검색과 원문 열람 모두에서 검증한다.
- 기준·문서 변경과 접근 철회 시 결과를 재확인 대상으로 전환하고 인덱스 갱신·삭제 전파 방법을 검증한다. 보존기간과 삭제 권한은 TS 정책 확인 후 설정한다.
- 기존 업무 화면을 복귀 경로로 보존하고 AI 기능만 비활성화할 수 있게 한다. 쓰기 도입 시 요청 식별자·상태 재조회·승인·중복 방지·복구 담당을 계약에 명시한다.

법정업무 확인 범위: 공식 자동차검사 업무·자동차관리법 제43조 등 안내 확인. 기한·수수료·판정은 공식 규칙으로 관리. 실제 현행 조문·위탁 관계·개인정보 처리 근거의 최종 적용 검토는 착수 전 확인 항목이다.
