## 2. 현행 기반과 고도화 목표

기계식주차장 검사·보수·재확인 자료을 이용하는 업무에 시설/검사 규칙·보수 대조·검사시스템 연계 항목을 추가한다. 현행 내부 화면·소요시간·API를 직접 시험한 것은 아니다. 아래 흐름과 오류 처리는 **제안 설계**이며 현업 워크숍에서 실제 절차와 대조한다.

대표 상황: 관리자가 보수를 완료했다고 제출했지만 지적된 장치와 작업 내용이 일치하는지 문서에서 불명확한 상황

| 현행 기반 활용 | 고도화할 처리 | 유지할 공식 책임 |
| --- | --- | --- |
| 기계식주차장 검사·보수·재확인 자료 | 기계식주차장 지적사항과 보수·재확인 증빙을 시설별로 연결하는 검사 후속 검토 지원 | 기존 업무의 자격·검사·예약·지급·공개·안전 판단 권한 |
| 시설별 보수 체크리스트와 기존 검사 관리시스템 | 지적사항과 보수 설명의 대응·누락·추가 확인 질문 | 원천 데이터·적용 기준의 승인과 검토자 확인 |


국민에게 기대하는 가치는 정확한 다음 행동과 보완 필요를 더 빨리 이해하거나, 담당자의 검토 누락을 줄이는 것이다. 다음 지표를 측정해 확인한다: 중요 보완 누락·시설/장치 오연결·추가 제출 왕복. 업무시간 절감을 감축 인원으로 환산하지 않는다. 사고 감소·무사고를 이 기능만으로 입증했다고 주장하지 않는다.

## 4. 처리 흐름과 화면

검사 결과 연결 → 보수 자료 제출 → 지적별 대조 → 검사관 검토 → 보완 또는 재확인 → 공식 결과 확인. AI는 기계 정상 작동을 판정하지 않는다.

| 순서 | 사용자·시스템 동작 | 처리 책임 |
| --- | --- | --- |
| 1 | 시설키와 지적 부위로 보수 자료를 연결한다. | LLM은 제안·설명, 규칙·권한·원천 상태는 응용 계층에서 검증 |
| 2 | 지적 항목의 요구 조치와 실제 텍스트 작업 범위를 비교한다. | LLM은 제안·설명, 규칙·권한·원천 상태는 응용 계층에서 검증 |
| 3 | 사진만 있는 증빙을 수동 검토 목록으로 분리한다. | LLM은 제안·설명, 규칙·권한·원천 상태는 응용 계층에서 검증 |
| 4 | 공식 재확인 결과를 읽어 검토 이력에 연결한다. | 사용자/현업 확인 후 공식 시스템의 권한 유지 |


화면 TS-P11-S01은 **입력·조건 → 근거를 포함한 결과 → 사용자/담당자 확인 → 다음 처리** 순서로 구성한다. 원문 위치와 적용본은 결과 옆에서 확인하고, 확인 전 초안과 확정된 원천 상태를 구분한다. 모바일은 입력·결과·확인을 세로로 배치하며 조건을 잃지 않는다.

| 화면 상태 | 필수 동작 |
| --- | --- |
| 대기·조회 중 | 입력을 보존하고 진행 단계 표시; 확정 버튼 중복 실행 방지 |
| 자료 없음·일부만 확인 | 없는 항목과 미확인 사유, 가능한 다음 행동 표시 |
| 권한 거부 | 자료 내용을 노출하지 않고 권한 요청 또는 기존 창구 안내 |
| 오류·시간 초과 | 현재 처리 결과를 확정하지 않음; 원 상태 재조회 후 재시도 |
| 정상 결과·확인 대기 | 근거·적용본·한계를 읽고 사용자가 선택 또는 담당자가 수정 |
| 이관·확정·반려 | 공식 응답이나 담당자 결정 이력으로 상태 구분 |


화면 상세 디자인과 API 실주소는 별도 구현 단계에서 확정한다. 키보드 입력·오류 초점·상태 읽기와 모바일 조건 유지가 제품 인수 시험 대상이다.

## 5. 데이터·출력 계약

아래 필드명은 **논리 설계 예시**다. 실제 원 시스템 필드·API가 존재한다는 뜻이 아니다. 필드별 필수 여부·보존기간·마스킹·추출 가능성을 원천 담당자와 매핑표로 확정한다.

| 입력 논리 항목 | 연결·검증 규칙 |
| --- | --- |
| facility_id / inspection_id | 시설·검사 식별자 |
| finding_id / component | 지적과 대상 부위·항목 |
| repair_ref / performed_at | 보수 설명·작업일·텍스트 증빙 |
| contractor_text / evidence_version | 제출 주체 설명과 증빙 버전 |
| recheck_required / result | 재확인 필요 여부와 공식 결과 |
| inspector_decision | 검사관의 최종 보완·종결 판단 |


출력은 다음 항목을 묶고 각 항목에 원문 참조·버전·확인 상태를 붙인다.

- 시설·검사·지적별 보수 대응표
- 보수 내용의 미확인 범위
- 타 시설·부위 증빙 불일치
- 현장 재확인 필요 목록
- 보완 요청 초안

공통 메타데이터: case_id, source_refs, source_version, retrieved_at, rule_version, model_config_version, review_status, reviewer_action. 여기의 review_status는 제안 기능의 상태이며 법정·업무 처분 상태를 대신하지 않는다.

시설·검사 결과 조회 1개와 텍스트 증빙 적재를 우선한다. 검사 결과 등록은 기존 시스템 권한을 유지하고 TS-BIZ-005의 동일 납품 범위를 대조한다.

자료가 없으면 승인된 파일 반입·공개 지식만으로 가능한 1단계까지 수행한다. 개인 데이터 조회·쓰기 연계가 필요한 후속 단계는 실제 인터페이스와 권한이 확인돼야 개발 범위를 확정한다.

## 8. 데이터 주권·안전·운영

수리 문서 확인이 시설 안전 확인으로 오인될 위험. 문서 검토와 검사관의 실물 확인을 상태에서 분리한다.

- 자료 원본·검색 인덱스·모델 호출·로그·백업·라이선스 경로를 기존 서버 환경에서 점검한다. 로컬 배치라는 이유만으로 외부 전송이 없거나 보안이 충족됐다고 단정하지 않는다.
- 문서 안의 명령·외부 링크는 근거 데이터로 취급하고 실행 지시로 사용하지 않는다. 인용 권한은 검색과 원문 열람 모두에서 검증한다.
- 기준·문서 변경과 접근 철회 시 결과를 재확인 대상으로 전환하고 인덱스 갱신·삭제 전파 방법을 검증한다. 보존기간과 삭제 권한은 TS 정책 확인 후 설정한다.
- 기존 업무 화면을 복귀 경로로 보존하고 AI 기능만 비활성화할 수 있게 한다. 쓰기 도입 시 요청 식별자·상태 재조회·승인·중복 방지·복구 담당을 계약에 명시한다.

법정업무 확인 범위: 공식 안내의 주차장법상 안전도 심사·사용/정기/정밀안전검사 확인. 개별 시행본·수탁 범위 대조 전. 실제 현행 조문·위탁 관계·개인정보 처리 근거의 최종 적용 검토는 착수 전 확인 항목이다.
