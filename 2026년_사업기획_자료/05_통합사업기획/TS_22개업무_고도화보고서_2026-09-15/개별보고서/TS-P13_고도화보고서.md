## 2. 현행 기반과 고도화 목표

자기인증 절차 안내·서식·기술기준·기존 가이드을 이용하는 업무에 제작자 절차 1종 지식·서식 대조·준비상태 UI 항목을 추가한다. 현행 내부 화면·소요시간·API를 직접 시험한 것은 아니다. 아래 흐름과 오류 처리는 **제안 설계**이며 현업 워크숍에서 실제 절차와 대조한다.

대표 상황: 처음 등록하는 제작자가 등록·기술검토·안전검사 단계별 제출자료를 구분하지 못하는 상황

| 현행 기반 활용 | 고도화할 처리 | 유지할 공식 책임 |
| --- | --- | --- |
| 자기인증 절차 안내·서식·기술기준·기존 가이드 | 자동차 제작자가 자기인증 절차의 준비자료와 기준 개정 영향을 확인하는 업무 지원 | 기존 업무의 자격·검사·예약·지급·공개·안전 판단 권한 |
| TS 기존 가이드 영상·문서·단계별 체크리스트 | 제작자 상황별 안내, 준비서류 비교, 적용기준 변경 영향 설명 | 원천 데이터·적용 기준의 승인과 검토자 확인 |


국민에게 기대하는 가치는 정확한 다음 행동과 보완 필요를 더 빨리 이해하거나, 담당자의 검토 누락을 줄이는 것이다. 다음 지표를 측정해 확인한다: 중요 서류 보완 누락·구기준 안내·추가 문의·준비시간. 업무시간 절감을 감축 인원으로 환산하지 않는다. 사고 감소·무사고를 이 기능만으로 입증했다고 주장하지 않는다.

## 4. 처리 흐름과 화면

제작자 유형 선택 → 절차·기준 고정 → 서식·증빙 대조 → 개정 영향 검토 → 보완 → 준비 상태 확인. 준비 완료는 자기인증 적합 판정이 아니다.

| 순서 | 사용자·시스템 동작 | 처리 책임 |
| --- | --- | --- |
| 1 | 제작자 유형·차종·절차로 요구자료를 선택한다. | LLM은 제안·설명, 규칙·권한·원천 상태는 응용 계층에서 검증 |
| 2 | 서식 필수 필드와 제출 증빙을 원문 위치로 연결한다. | LLM은 제안·설명, 규칙·권한·원천 상태는 응용 계층에서 검증 |
| 3 | 개정 조항·적용일·차종 범위를 분리해 영향 후보를 제시한다. | LLM은 제안·설명, 규칙·권한·원천 상태는 응용 계층에서 검증 |
| 4 | 담당자가 영향 후보와 보완을 검토하고 확정한 버전을 기록한다. | 사용자/현업 확인 후 공식 시스템의 권한 유지 |


화면 TS-P13-S01은 **입력·조건 → 근거를 포함한 결과 → 사용자/담당자 확인 → 다음 처리** 순서로 구성한다. 원문 위치와 적용본은 결과 옆에서 확인하고, 확인 전 초안과 확정된 원천 상태를 구분한다. 모바일은 입력·결과·확인을 세로로 배치하며 조건을 잃지 않는다.

| 화면 상태 | 필수 동작 |
| --- | --- |
| 대기·조회 중 | 입력을 보존하고 진행 단계 표시; 확정 버튼 중복 실행 방지 |
| 자료 없음·일부만 확인 | 없는 항목과 미확인 사유, 가능한 다음 행동 표시 |
| 권한 거부 | 자료 내용을 노출하지 않고 권한 요청 또는 기존 창구 안내 |
| 오류·시간 초과 | 현재 처리 결과를 확정하지 않음; 원 상태 재조회 후 재시도 |
| 정상 결과·확인 대기 | 근거·적용본·한계를 읽고 사용자가 선택 또는 담당자가 수정 |
| 이관·확정·반려 | 공식 응답이나 담당자 결정 이력으로 상태 구분 |


화면 상세 디자인과 API 실주소는 별도 구현 단계에서 확정한다. 키보드 입력·오류 초점·상태 읽기와 모바일 조건 유지가 제품 인수 시험 대상이다.

## 5. 데이터·출력 계약

아래 필드명은 **논리 설계 예시**다. 실제 원 시스템 필드·API가 존재한다는 뜻이 아니다. 필드별 필수 여부·보존기간·마스킹·추출 가능성을 원천 담당자와 매핑표로 확정한다.

| 입력 논리 항목 | 연결·검증 규칙 |
| --- | --- |
| manufacturer_type / process_step | 제작자 유형·선정 절차 단계 |
| vehicle_scope / reference_date | 대상 차종 범위와 적용 기준일 |
| requirement_id / version | 승인된 요구자료·기준 버전 |
| form_ref / field_map | 서식 버전·필수 필드와 증빙 |
| change_ref / effective_at | 개정 원문·시행일·경과 적용 확인 |
| preparation_status / reviewer | 준비 상태와 담당자 검토 |


출력은 다음 항목을 묶고 각 항목에 원문 참조·버전·확인 상태를 붙인다.

- 유형·단계별 준비자료표
- 서식 필드와 근거 대응
- 개정에 영향받는 서식 후보
- 적용일·범위 미확인 질문
- 담당자가 확정한 보완 목록

공통 메타데이터: case_id, source_refs, source_version, retrieved_at, rule_version, model_config_version, review_status, reviewer_action. 여기의 review_status는 제안 기능의 상태이며 법정·업무 처분 상태를 대신하지 않는다.

공식 절차·기준·서식의 승인본을 지식으로 적재하고 문서 조회를 연결한다. 등록·시험·인증 시스템 자동 처분은 포함하지 않는다. P14의 개정 대조·버전 관리 모듈을 공유한다.

자료가 없으면 승인된 파일 반입·공개 지식만으로 가능한 1단계까지 수행한다. 개인 데이터 조회·쓰기 연계가 필요한 후속 단계는 실제 인터페이스와 권한이 확인돼야 개발 범위를 확정한다.

## 8. 데이터 주권·안전·운영

절차 안내의 유효성을 기술 인증 적합성으로 확대 해석할 위험. 준비지원 범위와 공식 판정 주체를 표시한다.

- 자료 원본·검색 인덱스·모델 호출·로그·백업·라이선스 경로를 기존 서버 환경에서 점검한다. 로컬 배치라는 이유만으로 외부 전송이 없거나 보안이 충족됐다고 단정하지 않는다.
- 문서 안의 명령·외부 링크는 근거 데이터로 취급하고 실행 지시로 사용하지 않는다. 인용 권한은 검색과 원문 열람 모두에서 검증한다.
- 기준·문서 변경과 접근 철회 시 결과를 재확인 대상으로 전환하고 인덱스 갱신·삭제 전파 방법을 검증한다. 보존기간과 삭제 권한은 TS 정책 확인 후 설정한다.
- 기존 업무 화면을 복귀 경로로 보존하고 AI 기능만 비활성화할 수 있게 한다. 쓰기 도입 시 요청 식별자·상태 재조회·승인·중복 방지·복구 담당을 계약에 명시한다.

법정업무 확인 범위: TS 공식 자기인증 가이드 및 KATRI 조사 업무 확인. 제작자의 자기인증 책임과 TS 조사 역할을 구별. 실제 현행 조문·위탁 관계·개인정보 처리 근거의 최종 적용 검토는 착수 전 확인 항목이다.
