## 2. 현행 기반과 고도화 목표

데이터 개방센터 카탈로그·사전·이용 절차을 이용하는 업무에 공개 카탈로그 지식·신청 질문·반출 경계·오안내 평가 항목을 추가한다. 현행 내부 화면·소요시간·API를 직접 시험한 것은 아니다. 아래 흐름과 오류 처리는 **제안 설계**이며 현업 워크숍에서 실제 절차와 대조한다.

대표 상황: 이용자가 필요한 변수는 찾았지만 반출 가능 범위와 신청 목적을 혼동하는 상황

| 현행 기반 활용 | 고도화할 처리 | 유지할 공식 책임 |
| --- | --- | --- |
| 데이터 개방센터 카탈로그·사전·이용 절차 | 데이터 개방센터 공개 카탈로그를 이해하고 이용 신청 목적·항목을 준비하는 기존 지식서비스 확장 | 기존 업무의 자격·검사·예약·지급·공개·안전 판단 권한 |
| 검색 가능한 데이터 사전·이용 안내·정형 신청 양식 | 자연어 목적에 맞는 자료 후보 설명, 변수·제약 안내, 신청 준비 | 원천 데이터·적용 기준의 승인과 검토자 확인 |


국민에게 기대하는 가치는 정확한 다음 행동과 보완 필요를 더 빨리 이해하거나, 담당자의 검토 누락을 줄이는 것이다. 다음 지표를 측정해 확인한다: 변수 정의 오안내·권한 위반·신청 보완·분석 준비시간. 업무시간 절감을 감축 인원으로 환산하지 않는다. 사고 감소·무사고를 이 기능만으로 입증했다고 주장하지 않는다.

공개 NOA 소개와 내부 TA-01·02·03·20 기록은 재사용 후보의 근거다. 실제 납품 버전의 구현·성능·사용권 증명이 아니며 부족한 업무 기능은 CCK의 설정·개발·시험 과업으로 산정한다. TA-23 NL2SQL·Evidence Trail은 계획 기능이므로 현재 보유 기능으로 계상하지 않는다. 상세 기술 근거는 공통 보고서에 연결했다.

## 4. 처리 흐름과 화면

목적 확인 → 공개 카탈로그 검색 → 정의·제약 설명 → 신청 준비 점검 → 이용자 확인 → 담당자 심사. 자료 후보 제시는 이용·반출 허가가 아니다.

| 순서 | 사용자·시스템 동작 | 처리 책임 |
| --- | --- | --- |
| 1 | 공개 승인된 목록만 검색하고 존재·제공 범위를 근거로 표시한다. | LLM은 제안·설명, 규칙·권한·원천 상태는 응용 계층에서 검증 |
| 2 | 비슷한 이름의 필드를 정의·단위·집계 수준으로 구분한다. | LLM은 제안·설명, 규칙·권한·원천 상태는 응용 계층에서 검증 |
| 3 | 목적·필요 항목·이용 조건의 누락을 질문한다. | LLM은 제안·설명, 규칙·권한·원천 상태는 응용 계층에서 검증 |
| 4 | 공식 안내와 신청 준비만 제공하고 승인 상태를 생성하지 않는다. | 사용자/현업 확인 후 공식 시스템의 권한 유지 |


화면 TS-P20-S01은 **입력·조건 → 근거를 포함한 결과 → 사용자/담당자 확인 → 다음 처리** 순서로 구성한다. 원문 위치와 적용본은 결과 옆에서 확인하고, 확인 전 초안과 확정된 원천 상태를 구분한다. 모바일은 입력·결과·확인을 세로로 배치하며 조건을 잃지 않는다.

| 화면 상태 | 필수 동작 |
| --- | --- |
| 대기·조회 중 | 입력을 보존하고 진행 단계 표시; 확정 버튼 중복 실행 방지 |
| 자료 없음·일부만 확인 | 없는 항목과 미확인 사유, 가능한 다음 행동 표시 |
| 권한 거부 | 자료 내용을 노출하지 않고 권한 요청 또는 기존 창구 안내 |
| 오류·시간 초과 | 현재 처리 결과를 확정하지 않음; 원 상태 재조회 후 재시도 |
| 정상 결과·확인 대기 | 근거·적용본·한계를 읽고 사용자가 선택 또는 담당자가 수정 |
| 이관·확정·반려 | 공식 응답이나 담당자 결정 이력으로 상태 구분 |


화면 상세 디자인과 API 실주소는 별도 구현 단계에서 확정한다. 키보드 입력·오류 초점·상태 읽기와 모바일 조건 유지가 제품 인수 시험 대상이다.

## 5. 데이터·출력 계약

아래 필드명은 **논리 설계 예시**다. 실제 원 시스템 필드·API가 존재한다는 뜻이 아니다. 필드별 필수 여부·보존기간·마스킹·추출 가능성을 원천 담당자와 매핑표로 확정한다.

| 입력 논리 항목 | 연결·검증 규칙 |
| --- | --- |
| research_purpose | 이용 목적·필요 분석의 텍스트 |
| catalog_id / revision | 공개 데이터 목록과 개정일 |
| field_name / definition / unit | 공식 데이터 사전 항목·정의·단위 |
| granularity / coverage | 공간·시간 단위와 제공 범위 |
| access_condition / export_rule | 승인된 이용·반출 안내 |
| application_fields / missing_items | 신청서 목적·항목·보호 계획의 누락 |


출력은 다음 항목을 묶고 각 항목에 원문 참조·버전·확인 상태를 붙인다.

- 목적에 관련된 카탈로그 후보
- 정의·단위·기간·이용 제한
- 목적과 요청 항목의 대응표
- 신청 준비 보완 질문
- 담당 심사·반출 확인 경로

공통 메타데이터: case_id, source_refs, source_version, retrieved_at, rule_version, model_config_version, review_status, reviewer_action. 여기의 review_status는 제안 기능의 상태이며 법정·업무 처분 상태를 대신하지 않는다.

공개 카탈로그·사전·신청 안내 적재만 수행하며 원시 데이터 조회·NL2SQL·반출 쓰기는 0개다. TA-23의 계획 기능을 보유 기능으로 가정하지 않는다.

자료가 없으면 승인된 파일 반입·공개 지식만으로 가능한 1단계까지 수행한다. 개인 데이터 조회·쓰기 연계가 필요한 후속 단계는 실제 인터페이스와 권한이 확인돼야 개발 범위를 확정한다.

## 8. 데이터 주권·안전·운영

자료를 검색해 주는 기능이 데이터 이용 승인처럼 보일 위험. 제공 가능성과 개별 이용·반출 심사를 구분한다.

- 자료 원본·검색 인덱스·모델 호출·로그·백업·라이선스 경로를 기존 서버 환경에서 점검한다. 로컬 배치라는 이유만으로 외부 전송이 없거나 보안이 충족됐다고 단정하지 않는다.
- 문서 안의 명령·외부 링크는 근거 데이터로 취급하고 실행 지시로 사용하지 않는다. 인용 권한은 검색과 원문 열람 모두에서 검증한다.
- 기준·문서 변경과 접근 철회 시 결과를 재확인 대상으로 전환하고 인덱스 갱신·삭제 전파 방법을 검증한다. 보존기간과 삭제 권한은 TS 정책 확인 후 설정한다.
- 기존 업무 화면을 복귀 경로로 보존하고 AI 기능만 비활성화할 수 있게 한다. 쓰기 도입 시 요청 식별자·상태 재조회·승인·중복 방지·복구 담당을 계약에 명시한다.

법정업무 확인 범위: TS 데이터 개방센터 열람·분석 지원과 반출 제한 안내 확인. AI 학습·재배포 허용으로 확대하지 않음. 실제 현행 조문·위탁 관계·개인정보 처리 근거의 최종 적용 검토는 착수 전 확인 항목이다.
