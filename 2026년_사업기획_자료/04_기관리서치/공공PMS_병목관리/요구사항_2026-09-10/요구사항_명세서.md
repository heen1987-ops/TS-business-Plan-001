### 1.1 요구 표현

“해야 한다”는 해당 범위를 채택했을 때 충족할 **제안된 요구 조건**이다. 문구만으로 상세 설계 승인·기술 보장·법적 의무를 확정하지 않는다.

- M: 해당 연차 적용 범위에서 필수로 제안. C: 권한·자료·계약 등 선행조건 확인 후 채택할 조건부 요구.
- Y1/Y2/Y3: 최초 제공 연차. 먼저 제공한 요구는 후속 연차에도 적용.
- SFR: 기능, NFR: 품질·제약, DAR: 자료, IFR: 외부 연계, OPR: 운영, BMR: 도입·사업모델.
- 상세 요구에 미결 항목이 없더라도 공통 NFR·DAR·OPR와 기관별 TBD 조건은 적용된다.
- 요구 간 선행 관계는 범위·설계 의존성이다. 모든 이전 업무가 완료돼야 화면을 열 수 있다는 실행 순서를 뜻하지 않는다.
- 상위 원요구 PMS-R01~33과 SM/POL 출처는 추적표에서 확인한다. 상세 요구는 사용자 요구의 구체화 또는 서비스모델의 보완 제안이다.

### 1.2 정량 수용기준 확정 규칙

성능·AI 품질·보존기간·평가 가중치 등 미확정 값은 TBD로 남긴다. 수용평가 계획에는 지표·분모·측정 환경·자료 버전·목표·합격 임계값·책임자·예외를 함께 확정해야 한다. 미결 값이 있는 요구는 계약용 수용기준 확정본으로 간주하지 않는다.

품질은 AI의 단일 정확도나 일반 사용 사례의 절감률로 대체하지 않는다. BMR은 도입·책임·근거 문서로 검토하며 소프트웨어 동작 시험과 구분한다.

## 2. 용어·기본 단위

| 승인·확정 | 업무별 권한자가 특정 기준·대상 버전에 대해 내린 판단. 법정 감리 판단·계약 검수와 동일시하지 않음 |
| 다면평가 | 역할·관찰 범위·시점이 다른 참여자의 평가. 동일 점수의 반복 채점으로 취급하지 않음 |
| 수행 레퍼런스 | 기업의 실제 사업·역할·수행·개선·정정 근거가 연결된 이력. 자동 기업 등급이나 낙찰 결과가 아님 |
| 공통 검사 역량 | 기준·증거·검사·판단·조치·재검증·추적의 공통 기능. 분야별 법적 권한을 통합하지 않음 |

역할명만으로 모든 자료 접근을 허용하지 않는다. 실제 권한표는 기관·사업·자료 유형·행위·유효기간별로 TBD-02/07에서 정한다. 조회·검색·요약·내보내기·공유 결과에도 같은 범위가 적용돼야 한다.

## 4. 업무 상태·예외 명세

논리 상태는 업무 의미를 정의한다. 저장 방식·화면·API 상태값은 후속 상세 설계에서 정한다.

| 구분 | 주요 상태·전이 | 전이 조건·주체 | 금지·예외 |
| --- | --- | --- | --- |
| 기준선 | 작성/후보 → 공동 검토 → 확정 → 변경 검토 → 새 버전 확정 | 원문·적용 범위 확인, 지정자 확정 | 확정 원문·판단을 덮어쓰지 않음. 미확인은 임의 확정 금지 |
| 제출 | 작성/자체점검 → 제출 요청 → 접수 또는 접수 실패 → 새 버전/철회 이력 | 제출 권한·필수 형식·저장 결과 확인 | 업로드 미완료는 정상 접수와 구분. 접수 실패와 내용 부적합을 혼동하지 않음 |
| AI 분석 | 미요청 → 대기 → 처리 중 → 완료/일부 완료/실패/취소 | 입력·기준·실행 버전과 검사 범위 특정 | 일부 성공은 전체 완료로 표시 금지. 재시도와 신규 실행을 구분 |
| 기초 검토 | 후보 → 사람 확인 → 보완 요청/설명 요청/기각 → 응답 → 재검토 → 확정/미결/철회 | 검토자가 근거 확인, 권한자가 판단 | AI 후보를 즉시 미흡 사실로 확정하지 않음. 이견·자료 부족은 남김 |
| 보완·시정 | 요청 → 담당 배정 → 조치·소명 → 재검증 → 완료/재보완/보류 | 기준·증거·대상 버전 연결, 확인자 지정 | 파일 교체만으로 완료 금지. 새 버전에 과거 승인 자동 승계 금지 |
| 감리 Finding | 발견 후보 → 전문 확인 → 확정 또는 기각 → 시정 → 독립 확인 → 종료/잔여 | 감리 계약·범위에 따른 전문 판단 | 기관/CCK가 감리 결론을 단독 덮어쓰지 않음 |
| 평가 회차 | 계획 → 배정/수집 → 마감 → 확인 → 고지 → 소명/재검토 → 확정·정정 | 목적·척도·관찰기간·공개 범위에 따른 운영 | 미응답/관찰불가를 0점 처리 금지. 원응답과 운영 판단 분리 |
| 인수인계 | 준비 → 인계 요청 → 인수 확인/보완 → 승계 또는 미인수 | 후임 역할·미결 책임과 기한 확인 | 인사이동 사실만으로 모든 미결을 완료 처리 금지 |
| 유지관리 | 기산 확인 전 → 지원 중 → 준비 필요/종료 임박 → 종료 → 후속 계약 연결 | 하자·유상·제품지원별 계약 근거 | 일률적 기산일·기간 적용 금지. 종료가 미결 책임 삭제를 의미하지 않음 |

상태 변경에는 주체·대상·버전·시각·사유·근거를 연결한다. 상태 복구·철회는 이력을 남기는 새 사건으로 관리한다. 기록의 실제 보존·정정·폐기는 TBD-07 정책을 따른다.

## 5. 논리 자료사전

물리 테이블이나 API 스키마가 아닌 최소 업무자료 묶음이다. 자료 간 식별자·관계·버전·출처·확인 상태를 보존한다. 각 필드는 해당 사건이 발생했을 때 필요하며, 확정자·실제 완료일처럼 아직 발생하지 않은 값은 상태와 사유로 구분한다. 알 수 없는 값은 0·통과·완료로 대체하지 않는다.

## 9. 상세 요구사항

모든 요구는 검토안이다. 2개씩의 수용기준은 대표 성공·예외 조건이며, 기관별 상세 검증 계획에서 역할·자료·품질·복구 조건을 추가 구체화한다. 형식상 Given/When/Then은 사전조건/행동/기대결과를 뜻한다.
