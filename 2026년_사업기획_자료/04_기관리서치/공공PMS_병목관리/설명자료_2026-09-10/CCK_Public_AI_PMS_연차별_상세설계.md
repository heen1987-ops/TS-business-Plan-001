# Public AI-PMS 연차별·업무별 상세설계 v1.1

작성일: 2026-09-10. 대상: 사업기획자·발주기관·수행사 PM·설계자·감리 전문가.

**1차년도에는 사용할 수 있는 AI-PMS를 구축하고, 2차년도에 그 자료를 검사하는 감리 검사엔진을 구축한다. 3차년도에는 검증된 수행이력과 다면평가를 레퍼런스·성과환류·후속 발주에 활용한다.**

이 문서는 설계 제안이다. 실제 PMS·API·AI 엔진을 구현하거나 운영 성능을 검증한 결과가 아니다. [HTML 설명서](CCK_Public_AI_PMS_설명서.html) · [전체 설명 MD](CCK_Public_AI_PMS_설명서.md) · [정사각형 한 장 구조도](연차별_구조한장.svg)

## 2. 두 시간축을 분리한다

| 개발 연차 | 무엇을 만드는가 | 주요 납품물 | 다음 연차로 넘길 것 |
|---|---|---|---|
| Y1 · 1차년도 | AI-PMS 공동 사업관리 | 기준 확정, 일정·제출·보완, 기초 AI 지원, 기본 만족도·다면평가, 인수인계·유지관리 | 버전이 고정된 Baseline·원본·제출·권한·평가 시점·업무 이력 |
| Y2 · 2차년도 | 정보화사업 감리 검사엔진 | Control·Test·InspectionRun·Finding, 정보시스템 감리 기준팩, AI·사람 두 경로 | 검사 범위·오탐·미탐·확정/철회/정정 지적·시정·재검증 |
| Y3 · 3차년도 | 레퍼런스·성과환류 고도화 | 역할별 수행이력·다면평가 시계열·개선 대안·차기 RFP·기관별 설정 | 적용 규칙·활용 권한·비용·운영 책임과 검증 결과 |

**업무 B1~B3는 한 사업에서 반복되는 처리 단계다. Y1~Y3는 제품 개발 연차다.** Y1에도 기준설정·증거축적·기초 검토는 모두 있어야 한다. B3의 전문 검사·감리 연계 수준을 Y2에 높인다. Y3에 평가 화면을 처음 만드는 것으로 해석하지 않는다.

### 연차별 작업 묶음과 종료조건

| 연차 | 선행 → 구현 → 확인 순서 | 종료조건 제안 | 미충족 시 |
|---|---|---|---|
| Y1 | 실제 업무·기존 시스템 대조 → 권한·기준·업무상태 → 제출·원본·재시도 → AI 기초 지원 → 현장 사용 | 기준·접수·보완·소명·최신 버전 승인 흐름과 권한·복구 시나리오 통과. 기관·수행사 순업무시간과 입력 부담 측정 | 중복입력·권한·자료 품질부터 보완. Y2 검사 자동화를 확대하지 않음 |
| Y2 | Y1 자료 품질 평가 → 전문가 검사기준 정리 → 엔진·기준팩 → 블라인드 검토 및 분리 시험자료 평가 → 제한 적용 | 범위별 오탐·미탐·근거 정확성·검토부담을 사전 합의 기준으로 검증. 감리 판단권한과 차이 처리 확인 | 불확실·오류 영역은 수동 검토로 유지. 데이터·기준팩 수정 후 재평가 |
| Y3 | 평가 운영규칙 검토 → 역할별 이력 집계 → 정정·신규기업 처리 → 개선·RFP → 기관별 적용 검증 | 적법한 활용 범위와 평가 근거·표본·정정 반영 확인. 다음 기관에서도 권한·규칙·운영 책임 검증 | 기관 내부 참고로 범위 제한. 예측은 설명 가능한 현황·규칙 지표로 대체 |

기간이 지났다는 사실만으로 다음 단계의 성능·권한이 확보된 것으로 처리하지 않는다. 연차별 발주가 나뉘더라도 ID·버전·권한·상태·데이터 반출 형식의 호환성을 유지한다.

## 3. B1 사업등록·기준설정

### 사용자 목표와 기본 흐름

기관 담당자는 계약 의무·기한·검증방법과 책임을 확인하고, 수행사는 같은 기준에 의견을 남긴다. 권한자가 기준을 확정한다.

1. 사업·서비스·계약·기관·컨소시엄 실제 역할을 등록한다.
2. RFP·계약·협상 결과·제안서·수행계획·적용 지침을 원본과 버전별로 수집한다.
3. AI가 요구·의무·산출물·기한·시험조건 후보와 원문 위치를 추출한다.
4. 기관 검토자와 수행사가 적용 여부·책임·완료조건·일정에 의견을 남긴다.
5. 문서 충돌·모호한 범위·적용 근거 미확인은 쟁점으로 분리한다.
6. 권한자가 적용 기준과 미해결 항목의 처리 방침을 확인하고 확정한다.
7. Baseline 버전을 고정하고 WBS·제출 목록·평가 계획과 연결한다.

| 기준 필드 | 필수 의미 |
|---|---|
| baseline_id / version / status | 초안·공동검토·쟁점조정·승인·대체 버전 상태 |
| source_id / version / locator | 원문·문단·표·셀 등 검증 가능한 위치 |
| requirement_id / control_id | 요구사항과 검사할 세부조건의 관계. Y1은 확정 요구 중심, Y2에 Control 정교화 |
| obligation_type / applicability | 법적 의무·계약 의무·기관 규칙·권고, 적용 여부와 판단 근거 |
| responsible_role / reviewer / approver | 이행·검토·최종 확정 역할과 위임 유효기간 |
| due_date / acceptance / evidence_required | 합의 기한·완료조건·필요 증거와 확인방법 |
| effective_from / supersedes / change_reason | 변경 효력·이전 버전·사유·영향받는 항목 |
| evaluation_plan_id | 평가 대상·시점·역할·항목·이용 목적의 사전 정의 |

법·계약·기관 규칙·권고의 분류는 출처별 법적 우선순위를 자동 결정하는 알고리즘이 아니다. 계약 편입 여부, 적용 시점과 권한자의 판단을 기록한다. 필수 완료조건이 충돌하면 관련 항목은 확정을 보류하고 나머지 범위의 처리 가능 여부를 승인권자가 명시한다.

상태 제안: 초안 → 공동검토 → 쟁점조정 → 승인 → 후속 버전으로 대체. 반려는 초안 보완으로, 승인 후 변경은 새 변경요청으로 처리한다. 승인본을 덮어쓰지 않는다. 변경 전후의 제출·검사에 적용할 버전을 별도로 지정한다.

## 4. B2 공동 수행·산출물·Evidence

공유 사업공간, 기관 내부 공간, 수행사 내부 공간을 분리한다. 수행사 자체점검은 미제출 초안 영역에서 제공하고, 기관의 공식 평가 입력으로 자동 편입하지 않는다.

| 관리 단위 | 규칙 |
|---|---|
| 공동 WBS | 기관 자료 제공·검토·승인과 수행사 제출·보완, 외부 선행조건을 함께 관리 |
| 일정 | 최초 계획일·현재 승인일·예상일·실제일 분리. 예상일 변경은 승인일 변경 아님 |
| 진행 상태 | 작업 진척률·산출물 제출·검토·승인 상태 분리. 제출 수로 품질 완료율을 대체하지 않음 |
| 요청·회의 | 요청·회신·회의 결정의 대상·기한·확정자·근거 기록. 발언 초안과 확정 결정 분리 |
| 자발적 위험 신고 | 신고 자체에 벌점을 부여하지 않음. 예측 위험과 확정 사건·책임 구별 |
| 컨소시엄 | 회사×사업×실제 역할×기간을 연결. 총괄사 점수를 참여사에 일괄 복사하지 않음 |
| 접수 | 권한·대상·필수 형식 확인 → 제출본 원본·버전 고정 → 접수증 → 검토 업무·분석 작업 생성 |

Evidence는 파일 유무를 넘어서 출처·생성 맥락·어떤 주장을 뒷받침하는지를 기록한다.

| Evidence 필드 | 규칙 |
|---|---|
| evidence_id / source_type | 문서·시험 로그·시스템 기록·확정 회의·결정 등 유형 |
| object_id / version / hash | 원본 객체·버전·파일 무결성 정보. hash만으로 사실성·검사 적합성 보장 불가 |
| producer / collected_at / occurred_at | 작성·수집 주체와 수집시각·실제 발생시각 분리 |
| locator / requirement_links | 페이지·셀·로그 구간과 요구사항의 다대다 연결 |
| classification / acl / retention | 기밀·개인정보·영업정보 분류, 이용권한·보존 정책 |
| provenance / verification_status | 자체 주장·확정 기록·시스템 수집 등 출처와 확인 상태 |
| extraction_status / missing_scope | 추출 실패·일부 성공·읽지 못한 구간. 없다는 결론과 분리 |

출처 유형을 일률적인 A~E 신뢰 점수로 확정하지 않는다. 공식 문서에도 오류가 있을 수 있고 시스템 로그에도 설정 누락이 있을 수 있다. 출처·무결성·독립 확인·주장 대응성을 각각 보여준다.

업무 접수와 AI 분석은 서로 다른 상태다. 파일 저장 중 실패하면 접수 성공을 표시하지 않는다. 저장·DB 등록을 확인한 접수는 분석 장애로 취소하지 않는다. 재시도 시 동일 접수증을 반환하고 검토 업무·분석 작업 중복을 막는다. 파일만 저장되고 DB 처리가 실패한 항목은 미완료 접수로 표시해 재처리·보정한다.

## 5. B3 검사엔진·사람 검토·감리

### Y1과 Y2의 경계

| Y1 기초 AI 지원 | Y2 감리 검사엔진 |
|---|---|
| 문서 분류·원문 탐색·요구 후보·필수 항목·증빙 누락 후보 | 확정 Control·Test와 요구사항별 검사계획·실행·범위 기록 |
| 담당자 수동 검토·기본 이슈·보완 이력 | 구조화 Finding·전문검토·AI와 감리 경로 대조·시정 재검증 |
| 문서·업무관리 편의 및 자료 품질 확인 | 영역별 검사 성능·미탐·오탐·근거 정확성과 감리 활용 검증 |

검사 연결: Standard → Control → Object → Evidence → Test → InspectionRun → FindingCandidate → Review → Action → Retest → Conclusion.

검사 범위는 완전성, 요구 적합성, 문서 정합성, 추적성, 증빙 충분성, 변경 반영, 일정·절차, 반복 위험 후보로 나눈다. 날짜·필수값은 규칙, 의미 대조는 LLM, 실행 결과는 시험·정적분석·보안 등 해당 전문도구의 증거를 사용한다. 문서만으로 실제 보안·성능·접근성 충족을 확정하지 않는다.

| 검사 출력 | 의미와 후속 |
|---|---|
| 근거 확인 | 해당 검사·버전·범위에서 확인. 전체 시스템 적합 판정 아님 |
| 부분 확인 / 증거 미확보 | 부족한 범위와 추가 자료 요청 |
| 불일치 후보 | 상충 원문 위치와 기준 버전 제공, 사람 검토 |
| 적용 제외 후보 | 적용 여부를 권한자가 확인해야 제외 확정 |
| 전문검토 필요 | 문서만으로 결정 불가, 담당 전문가·감리 검토로 전달 |
| 판정 불가 / 기술 실패 | 추출·권한·도구·증거 제한 이유 제공, 통과로 집계하지 않음 |

각 실행은 baseline_version, submission_version, control_version, test_version, evidence_ids, model_version, prompt_version, run_id, 시작·종료·실패 상태, 실행자·접근범위를 남긴다. 동일 조건의 검사도 LLM 재실행 결과가 달라질 수 있으므로 입력과 출력 이력을 보존한다.

Finding은 관찰 사실·미확보 증거·해당 요구·원문 위치·AI 해석·추천 조치·중요도 후보·공식 상태를 분리한다. AI confidence는 보정 실험 전 정확률로 표기하지 않는다. 확정된 부적합과 기업 귀책 판단도 별도다.

상태 제안: 후보 → 검토 중 → 확인/추가 자료/철회/전문검토 → 보완·소명 → 재검증 → 해결/미해결/정정/유보. 사람은 AI가 찾지 못한 지적도 새로 등록한다. 지적의 철회·정정은 해당 수행이력과 후속 조회에 반영하며 원래 판단은 변경 이력으로 보존한다.

### AI와 감리사의 두 경로

같은 허용 증거를 보되 AI 결과를 열람하기 전 독립 검토 표본을 먼저 확보할 수 있도록 한다. 운영 중 AI 후보를 보고 검토한 결과와 블라인드 평가 결과를 구분한다.

| AI / 사람 | 처리 |
|---|---|
| 둘 다 발견 | 같은 지적인지·근거 충분성·중요도 확인. 합의만으로 정답 확정 금지 |
| AI만 발견 | 오탐 또는 사람 누락 가능성을 독립 검토 |
| 사람만 발견 | AI 미탐·입력 누락·검사 범위 차이를 분류 |
| 둘 다 미발견 | 별도 전문가 기준답안·표본 재검사·후속 사건으로 누락 확인 |

감리의 법적 판단 주체·서명·독립성은 해당 사업의 적용 제도에 따른다. 이 제품의 내부 검토를 법정 감리나 계약상 검사·검수 승인으로 자동 치환하지 않는다.

## 6. 주기적 다면평가와 기업 레퍼런스

### 역할과 관찰 범위

| 역할 ID | 평가자 | 관찰 범위 |
|---|---|---|
| EV01 | 직접 담당자 | 협업·요청 대응·합의 일정의 이행 맥락 |
| EV02 | 산출물·기술 검토자 | 검토한 요구·시험 증거·보완 품질 |
| EV03 | 중간관리자 | 쟁점 보고·의사결정 지원·위험 대응 |
| EV04 | 최종 결재자·책임자 | 사업목적·중요 결정·확정 성과 |
| EV05 | 관련 업무부서 | 업무 적합성·요구 반영·전환·교육 |
| EV06 | 실서비스 사용자 | 이용 편의·접근성·문제 해결 경험 |
| EV07 | 감리원·전문가 | 검증 범위의 적합성·근거·시정 확인 |

착수에 계획을 정하고, 정기 점검·주요 산출물·시험·종료·운영 사건에 맞춰 평가한다. 주기는 사업별 설정한다. 평가자는 업무 참여·관찰 범위와 평가 기간을 등록한다. 직급이 높다는 이유로 모든 항목을 평가하거나 자동 가중하지 않는다.

### 세 종류의 기록을 함께 보여준다

1. 수행 사실: 승인 기한, 제출, 보완, 확정 품질, 귀책 판단과 예외.
2. 검사·감리 결과: 범위·근거·확정·철회·정정·조치·재검증.
3. 사람의 평가: 평가자 역할·관찰 기간·질문·응답·근거·응답 여부.

이 세 기록을 하나의 객관적 사실로 합치지 않는다. 협업 만족도, 산출물 만족도, 공공서비스 만족도, PMS 사용 만족도는 대상이 다르므로 별도 집계한다.

### 점수·가점·감점의 설계 제안

초기 화면은 항목별 평가와 확인 사실을 제공한다. 척도 후보는 1 매우 미흡 / 2 미흡 / 3 기준 충족 / 4 우수 / 5 매우 우수 / 관찰 불가이다. 각 항목별 행동·결과 예시를 사전에 정하고 동일 의미로 사용한다. 확정된 평가 규정이 아니라 현장 검증할 초안이다.

- 우수 수행은 확인된 성과와 근거를 긍정적 레퍼런스로 제시한다. 미흡 수행은 확정된 내용·영향·소명·개선 결과와 함께 제시한다.
- 내부 점수 증감이 필요하면 사전 합의된 항목·가중치·예외·이용 목적을 적용한다. 임의의 기본점수·가중치·감점표는 이번 설계에서 확정하지 않는다.
- 지연 일수·보완 횟수·AI 후보 수·위험 신고 수를 자동 벌점으로 바꾸지 않는다. 기관 대기·범위 변경·난이도·실제 책임을 확인한다.
- 관찰 불가·미응답은 0점이 아니다. 평가 대상 수·응답 수·관찰 범위·자료 충분성을 함께 표시한다.
- 여러 평가자의 같은 사건을 중복 가산·감산하지 않는다. 같은 역할의 다수 응답이 다른 역할의 관점을 덮지 않도록 역할별 집계와 분포를 먼저 제공한다.
- 신규기업의 이력 없음은 미평가로 표시한다. 참여자격 판단과 구별하고, 같은 제출 전 점검·명확한 기준·소명 기회를 제공한다.
- 공식 입찰 가점·감점·제재·기관 간 공유는 별도 법적 근거·절차·권한 확인 대상이다. 내부 참고 점수를 자동 전송하는 API를 기본 제공하지 않는다.

종합점수가 후속 요구로 확정될 때만 항목별 유효 응답·역할 집계·가중치·자료 충족 기준·이의 처리·정정 재계산 규칙을 먼저 합의한다. 이력이 적은 기업과 큰 사업을 수행한 기업의 단순 평균 순위를 공정성의 증거로 삼지 않는다.

### 평가 운영 흐름

계획 사전 고지 → 역할·대상 배정 → 관찰 범위 응답 → 근거·중복 검토 → 공개 범위에 따른 결과 통지 → 소명·정정 → 확정·버전 이력 → 후속 조회 반영.

평가 원문과 평가자 신원·개별 응답의 공개 범위는 따로 정한다. 소규모 집단은 집계만으로도 개인이 식별될 수 있으므로 최소 집계조건을 기관 정책으로 결정한다. 근거 없는 악의적 평가는 검토 대상으로 보류하고 원문·처리 사유를 권한 범위에서 보존한다. 이해충돌 신고·회피와 평가자 변경 이력을 남긴다.

### 대안과 권고

**B 권고.** 초기에는 업무 모듈과 분석 작업자를 논리적으로 분리하고 기존 시스템·운영 능력에 맞춰 배치한다. 마이크로서비스·외부 모델·특정 클라우드를 선결정하지 않는다. 검사 처리량·독립 배포·보안 경계가 분명해지면 Y2에 엔진의 실행 단위를 분리한다. Y1 사용자·권한·제출 기능은 호환성을 유지한다.

### 주요 관계

| 관계 | 수량·의미 |
|---|---|
| Service ↔ Project ↔ Contract | 서비스에 여러 사업·계약, 동시 운영·고도화 가능. 연결 역할·기간 명시 |
| Project → Baseline → Requirement | 한 사업의 기준 버전별 요구 목록 |
| Requirement ↔ Task / Deliverable | 요구와 과업·산출물의 다대다 대응 |
| Deliverable → Submission → Evidence | 산출물별 여러 제출 버전, 증거의 재사용 연결 |
| InspectionRun → Finding → Review / Action / Retest | 실행 버전·검토·보완·소명·재검증의 연속 이력 |
| EvaluationPlan → EvaluationRound → Response | 평가 목적·시점·역할·관찰 범위 |
| Company ↔ ProjectRole → ReferenceEntry | 실제 수행 역할·기간·확정 근거·정정 버전 |

기준·산출물·검사·평가에는 사업·기관 경계, 작성자, 작성시각, 상태, 원본 위치, 유효 버전을 공통으로 둔다. 동시 수정은 버전 비교로 충돌을 알리고, 철회는 기록 삭제 대신 상태·근거로 관리한다. 보존기간·삭제·정정 정책은 적용 법령·기관 규정과 함께 설계하며 모든 기록을 무기한 보관하지 않는다.

### API 계약 초안

다음 경로는 설계용 이름이며 구현된 API가 아니다. 모든 요청은 기관·사업·역할·객체 권한을 서버에서 검증한다.

| API 제안 | 입력·결과 | 권한·상태 조건 | 실패·재시도 |
|---|---|---|---|
| POST /projects | 서비스·계약·역할 → project_id | 기관 사업 생성 권한 | 중복 키 확인 |
| POST /projects/{id}/baselines/drafts | 원문 버전 → draft_id | 해당 사업 기준 편집 | 추출 일부 성공 표시 |
| POST /baselines/{id}/approve | 대상 버전·결정 근거 → 승인 버전 | 승인권자·미해결 충돌 처리 | 409 버전 충돌, 사유 표시 |
| POST /deliverables/{id}/submissions | 원본·증거·기준 버전 → 접수증 | 제출 권한·필수 형식 | Idempotency-Key, 저장 실패 시 성공 금지 |
| GET /submissions/{id}/analysis | run_id·진행·오류 범위 | 해당 제출본 열람 권한 | timeout 표시·접수 상태 유지 |
| POST /inspection-runs | 대상 고정 버전·검사팩 → run_id | Y2 검사 실행 권한 | 202 접수, 중복 사건 처리 |
| POST /findings/{id}/reviews | 근거·판단·보완·소명 → review_id | 배정 검토자·위임 | 현재 버전 확인, 충돌 시 재검토 |
| POST /findings/{id}/retests | 수정 증거·대상 버전 → retest_id | 검토·전문가 권한 | 구버전 결과로 최신본 종결 금지 |
| POST /evaluation-rounds/{id}/responses | 역할·관찰 범위·응답·근거 → 응답 ID | 해당 시점 배정 평가자 | 이중 응답·마감·평가 대상 검증 |
| GET /companies/{id}/references | 기간·사업·역할 → 허용 이력 | 목적·공개 범위·기관별 권한 | 자료 없음은 빈 상태·미평가 |

오류는 403 권한 없음, 409 상태·버전 충돌, 422 입력 오류, 503 일시 실패 등으로 구분한다. 존재 여부 자체가 비공개인 자료는 일관된 비노출 응답 정책을 적용한다. 조회·다운로드·검색·캐시에도 동일 권한을 적용한다.

이벤트 초안: BaselineApproved, SubmissionAccepted, EvidenceAdded, BaselineChanged, InspectionCompleted, FindingCorrected, EvaluationFinalized. event_id·entity_version·occurred_at·처리 이력을 두어 중복·순서 역전을 감지한다. 오래된 분석·평가 결과가 최신 상태를 덮지 않게 한다.

| Permission denied | 접근 범위와 요청 경로, 비공개 원문·다른 조직 존재정보 노출 방지 |
| Disabled | 승인본 수정·구버전 종결 등 제한 이유와 변경 요청 경로 |
| Offline / Retry | 전송 전·접수 여부 미확인·접수 완료를 구별, 복구 후 중복 제출 방지 |

본 설명 HTML은 위 제품 화면의 구현물이 아니다. 제품 화면 시안·실제 데이터·서버 권한·스크린리더 검증은 다음 구현 범위다. 이번 HTML에는 연차 선택, 업무 상세 설명, 역할별 평가 기준, 기존 단계 설명·편익 계산을 제공한다.

### 제품 BDD 시나리오 초안 — 아직 실행하지 않음

- PMS-AT04: Given 계약과 계획의 성능조건 충돌, When 담당자가 승인, Then 관련 항목의 충돌 사유·해결 근거가 없으면 확정을 막고 쟁점으로 유지한다.
- PMS-AT05: Given 파일·업무 DB 정상 접수 후 분석 장애, When 재시도, Then 최초 접수시각·원본 버전·접수증을 유지하고 추가 접수·검토 업무를 만들지 않는다.
- PMS-AT06: Given 버전 2 제출 후 버전 1 검사 완료, When 결과 도착, Then 과거 분석으로 연결하고 버전 2를 자동 승인하지 않는다.
- PMS-AT01: Given AI와 감리사가 동일 항목을 미발견, When 독립 기준답안에 결함 존재, Then 합의 정상으로 제외하지 않고 미탐에 포함한다.
- PMS-AT02: Given 평가 배정이 없는 관련부서 사용자, When 응답 제출, Then 거절한다. 배정자는 관찰 불가를 선택할 수 있고 0점으로 계산하지 않는다.
- PMS-AT03: Given 잘못된 지적이 철회된 기업, When 후속 이력 조회, Then 정정된 상태와 근거를 반환한다. 신규기업의 빈 이력은 불리한 등급으로 변환하지 않는다.

## 10. 연차별 정량 편익과 실증 계획

HTML의 기존 계산기는 **하나의 운영 기간에 대한 설명용 가상 계산**이다. 비용 배분 기본값 3년과 제품 개발 3개년 계획은 서로 다른 개념이다. Y1부터 Y3의 모든 효과가 발생한다고 가정하거나 기존 289시간을 실증 계수로 사용하지 않는다.

| 연차 | 우선 검증할 효율·품질 | 측정단위·방법 | 금전 산정 경계 |
|---|---|---|---|
| Y1 | 탐색·취합·제출·인수인계·감리자료 준비 | 역할별 동일 업무의 순소요시간, 중복 입력·추가 확인 포함 | 감리 엔진의 전문 검사 효과를 선반영하지 않음 |
| Y2 | 순검토시간·중요 누락·조기 발견·보완 반복 | 난이도·범위를 맞춘 규칙/AI/전문가 비교, 오탐·미탐·검토시간 포함 | Y1 증거 준비 시간과 중복 금지. 위험회피 비용은 별도 사건·기여도 입증 |
| Y3 | 평가 근거·정정 반영·업무 연속성·서비스 품질 | 역할별 표본·응답률·분포, 비교 가능한 후속 사업·서비스 지표 | 공정성·카르텔 감소·업체선정 성공을 임의 금액으로 환산하지 않음 |

연차 t의 직접 시간가치 = Σ(실제 적용 업무량 × 해당 기간의 순시간 차이 × 역할별 적용 단가). 신규 입력·오탐 수정·운영 지원을 해당 순시간 또는 비용 중 한 곳에서 차감한다.

연차 t 순비용차이 = 검증된 직접 시간가치 + 별도 입증된 비중복 편익 − 해당 연차 구축·연계·이관·교육·모델·운영·재검증 비용. 현금흐름과 시간가치는 구분해 표기한다.

정식 경제성 분석에서는 효과 발현 시점·도입률·운영 기간·할인율·잔존가치·불확실성 범위를 사업 조건에 맞게 확정한다. 여기서는 정식 B/C·NPV를 계산하지 않았다.

### 측정과 합격 기준을 정하는 방식

| 지표 | 산식·환경 | 목표·임계값 확정 시점 | 책임 |
|---|---|---|---|
| 순업무시간 | 같은 업무·자료·난이도에서 현행 대비 총소요시간 차이. 학습·등록·오탐 시간 포함 | 실증 시작 전 최소 유의 개선폭·허용 품질 저하를 합의. 수치 미확정 | 실증 책임자·현업 |
| 검사 정밀도·재현율 | 독립 전문가 기준답안에 대한 확정 검출·오탐·미탐. 중요도별 구분 | 검증 표본 설계 때 허용 미탐·오탐과 불확실성 구간 정의 | 감리·품질 전문가 |
| 근거 정확성 | 제시 원문이 해당 주장을 실제 뒷받침하는 검사 비율 | 출처 유형·문서 품질별 목표 합의 | 기준팩 책임자 |
| 평가 근거·정정 | 유효 근거 연결 비율·정정 완료부터 후속 조회 반영까지 시간 | 평가 운영규칙 확정 전 목표·공개 범위 합의 | 평가 운영자 |
| 데이터·권한 무결성 | 중복 접수·버전 뒤바뀜·무권한 조회의 정의된 시험 | 정의된 필수 수용 시나리오 전부 통과, 미해결 중대 결함 없음 | 개발·보안·QA |

외부 지식업무 연구의 생산성 수치는 현장 효과의 확정 계수가 아니다. AI 결과를 본 감리원의 동의율만으로 정확도를 측정하지 않는다. 자료·사업 단위로 학습/개선용과 최종 검증용 표본을 분리한다. 동일 산출물의 다른 버전이 양쪽에 섞여 성능이 부풀려지지 않도록 한다.

## 11. 보안·운영·연차 전환

- 기관·사업·조직·역할·문서 수준의 권한을 원본·검색·임베딩·캐시·다운로드에 일관되게 적용한다. 권한 철회·담당자 교체·계약 종료 시 조회와 대기 작업의 권한을 다시 확인한다.
- 업로드 문서는 검사할 데이터다. 문서 안의 명령으로 시스템 정책·검사기준·외부 도구 호출을 바꾸지 않는다. 분석 실패 시 임의의 외부 모델로 자료를 보내지 않는다.
- 민감정보·영업정보·평가자 신원은 목적에 맞게 최소 처리한다. 로그는 비밀값과 원문 전체를 무분별하게 남기지 않는다.
- Y2 도입은 기존 Y1 식별자·승인본·접수증을 유지하며 새 검사 객체를 추가한다. 이관은 건수·연결·버전·권한을 대조하고 복구 가능한 백업에서 시험한다.
- 기능별 사용 전환 설정으로 검사 작업을 중지해도 공동 제출·검토는 유지한다. 기준팩·모델 버전 변경 시 기존 결과를 덮어쓰지 않고 새 실행으로 기록한다.
- 운영 지표는 접수 실패·분석 대기시간·재시도·추출 실패·권한 거절·정정 미반영·사용자 부담으로 시작한다. 경보값과 담당자는 실제 환경에서 합의한다.
- 롤백은 이전 기능·기준팩으로 복귀하되 확정된 접수·보완·정정 사실은 삭제하지 않는다. 데이터 호환성·대기 작업 처리·복구 후 재검사를 릴리즈별로 명시한다.
